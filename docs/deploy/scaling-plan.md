# План масштабирования установок (онбординг клубов)

> Цель: довести установку нового клуба от ~1 рабочего дня до 15–30 минут,
> с минимумом ручной работы, чтобы продукт можно было продавать как «коробку»
> или SaaS, а не как кастомную интеграцию.

## 1. Текущее состояние (что у нас есть)

- **Архитектура — строго single-tenant**: в коде нет `tenant_id` / `club_id`,
  модуль `club` рассчитан на **один клуб на инсталляцию**.
- **Деплой**: один VPS = Postgres + API (бот в процессе) + Caddy + статика
  Mini App / Admin. Развёртывание описано в `docs/deploy/deploy-steps.md`.
- **Что делается руками** (≈10 ручных шагов сейчас):
  1. Покупка домена
  2. Создание VPS на HOSTVDS
  3. Настройка DNS (3 A-записи)
  4. Установка Docker и UFW
  5. Клонирование репо и заполнение `.env.prod`
  6. Запуск `docker compose`
  7. Регистрация бота в @BotFather + привязка Mini App
  8. Создание админа через `psql` (`bcrypt` руками)
  9. Наполнение клуба, тренеров, расписания
  10. Приёмка
- **Что отсутствует** для масштабирования:
  - Авто-бэкапы БД
  - Централизованный мониторинг (uptime, ошибки)
  - Самообслуживание клиента (онбординг без участия разработчика)
  - Биллинг и подписочная модель
  - Мульти-арендность (одна инфраструктура → много клубов)

---

## 2. Три варианта масштабирования (с компромиссами)

### Вариант A. Автоматизация single-tenant
Сохраняем модель «один VPS на клуб», но всё ставится скриптом за 15 минут.

**Плюсы:**
- Минимум изменений в коде продукта (только скрипты + один раз бэкапы и мониторинг).
- Полная изоляция клиентов: один упал — остальные живы.
- Можно продавать как «коробочный продукт» под ключ.
- БД клиента физически у клиента — проще с 152-ФЗ (ПДн).

**Минусы:**
- Стоимость на масштабе: 50 клубов = 50 VPS ≈ $150–300/мес инфраструктуры.
- N доменов, N ботов, N сертификатов — больше внешних поверхностей для отказов.
- Обновления — пройти по всем серверам (можно автоматизировать, но всё равно N деплоев).
- Поддержка тяжелее: баг у одного клиента нужно воспроизводить отдельно.

**Когда подходит:**
- 1–20 клубов
- B2B-продажа с высоким чеком (есть бюджет на инфру)
- Корпоративный клиент хочет «свой» сервер

---

### Вариант B. Multi-tenant SaaS (одна инсталляция на всех)
Все клубы живут в одной БД, изоляция через `tenant_id` (или Postgres RLS).
Один домен, поддомены вида `<club>.fitscheduler.app` или путь `/club-slug`.

**Плюсы:**
- Дешёвая инфра: один сервер тянет десятки клубов до определённого предела.
- Один деплой обновляет всех.
- Self-service регистрация: клуб сам создаёт аккаунт через лендинг.
- Биллинг встраивается естественно (Stripe / CloudPayments → подписка).

**Минусы:**
- **Серьёзный рефакторинг кода:**
  - Добавить `tenant_id` (или `club_id`) во все таблицы и индексы.
  - Middleware изоляции: каждый запрос знает свой `tenant_id` из JWT.
  - Один Telegram-бот не может обслужить всех — нужен **мульти-бот**:
    либо N webhooks на один процесс (по `secret_token`), либо общий
    «диспетчер»-бот с deeplink на клуб.
  - Mini App и Admin — нужно по URL определять текущий клуб.
- Один баг ронит всех клиентов.
- ПДн всех клубов в одной БД — требования к безопасности выше.
- Сложнее уйти на on-premise по запросу VIP-клиента (если потребуется).

**Когда подходит:**
- 20+ клубов
- Низкий-средний чек, B2C-канал привлечения
- Готовность инвестировать 1–3 месяца в рефакторинг

---

### Вариант C. Гибрид (рекомендуется)
Идти этапами: сначала автоматизация single-tenant, потом мульти-арендность
для SMB, dedicated-инсталляция как премиум-тариф.

**Логика:**
1. **Месяц 1–2:** автоматизировать текущую модель — продавать первым 5–10 клубам.
2. **Месяц 2–4:** ввести `tenant_id` в БД и API, поднять второй вариант
   деплоя — shared SaaS на одном VPS.
3. **Месяц 4–6:** биллинг, self-service регистрация, лендинг.
4. **Дальше:** dedicated-инсталляция остаётся как VIP-тариф (тот же код, тот же
   скрипт, но отдельный VPS — продаётся дороже как «приватный сервер»).

Реальные клиенты на первом этапе оплатят разработку второго.

## 3. Дорожная карта (рекомендуемый путь)

### Этап 1. Автоматизация single-tenant (1–2 недели)

Цель: установка нового клуба от A до Я скриптом за 15 минут.

#### 1.1. Скрипт `install.sh` на сервере
Принимает все параметры через флаги/env, делает всё что сейчас в `deploy-steps.md`.

Файл: `scripts/install.sh`
```bash
#!/usr/bin/env bash
set -euo pipefail

# Использование:
#   curl -fsSL https://raw.githubusercontent.com/<repo>/develop/scripts/install.sh | \
#     bash -s -- --domain club.ru --email me@club.ru --bot-token XXX

DOMAIN=""
ACME_EMAIL=""
TG_BOT_TOKEN=""
# … разбор флагов

# 1. Установка Docker, UFW
# 2. Генерация секретов: JWT_SECRET, TG_WEBHOOK_SECRET, NX_DB_PASS
# 3. git clone и cd
# 4. Запись .env.prod из шаблона
# 5. docker compose up -d --build
# 6. Ожидание готовности API (healthcheck)
# 7. Создание первого админа (email/пароль из флагов)
# 8. Вывод: URL'ы, логин, пароль, инструкция для BotFather
```

Что внутри скрипта обязательно:
- Идемпотентность: повторный запуск не ломает инсталляцию.
- Проверка DNS перед стартом Caddy (`dig +short api.$DOMAIN`).
- Sanity-check: достаточно ли RAM, есть ли swap.
- Печать чек-листа «что осталось сделать руками» в конце.

#### 1.2. Автоматизация DNS (опционально, если регистратор поддерживает API)
- reg.ru, beget — есть REST API. Можно создать 3 A-записи скриптом.
- Если регистратор без API — оставить ручной шаг с понятным сообщением.

#### 1.3. Авто-бэкапы БД
Файл: `scripts/backup.sh` + cron-job в `docker-compose.prod.yml`.
- `pg_dump` каждые 24 часа.
- Хранение: 7 ежедневных + 4 еженедельных + 3 ежемесячных.
- Загрузка во внешнее хранилище (S3-совместимое — Selectel/Yandex Object Storage).
- Алерт в Telegram, если бэкап не выполнился.

#### 1.4. Мониторинг
- `uptimerobot.com` (free) для каждого `api.<domain>/health` — алерт в Telegram.
- Sentry для backend (уже подключен в `apps/api/src/instrument.ts` — проверить
  и завести один общий проект, теги по `DOMAIN`).
- Логи — пока `docker logs`, отдельный стек (Loki/Grafana) — позже.

#### 1.5. Onboarding-форма для менеджера
Простой Notion/Google Form: клиент заполняет 10 полей →
автоматически генерируется команда `install.sh ...` для запуска.
Поля: домен, email, юр.лицо, контакт, бренд-цвета, и т.д.

**Итог этапа 1:**
- Время установки клуба: 15–30 минут (вместо ~1 рабочего дня).
- Один человек поддерживает ~10–20 клубов.
- Готовность продавать «коробку».

### Этап 2. Мульти-арендность (3–6 недель)

Цель: одна инсталляция обслуживает много клубов.

#### 2.1. Изменения в БД
- Добавить таблицу `tenants` (`id`, `slug`, `name`, `plan`, `is_active`, `created_at`).
- Добавить колонку `tenant_id` во **все** доменные таблицы:
  `clubs`, `coaches`, `customers`, `schedule_*`, `membership_plans`, `admin_users`, …
- Создать составные индексы `(tenant_id, …)` под основные запросы.
- Опционально: Postgres **Row Level Security** (`CREATE POLICY`) как
  defense-in-depth поверх middleware. RLS медленнее, но защитит от багов
  «забыл where tenant_id».

#### 2.2. Изменения в API (NestJS)
- `TenantContextMiddleware`: извлекает `tenant_id` из JWT и кладёт в `AsyncLocalStorage`.
- Все репозитории фильтруют по `tenant_id` через TypeORM `subscriber` или
  глобальный `where` (или RLS).
- Тесты-гварды: интеграционные тесты с двумя tenant'ами, проверяющие изоляцию.

#### 2.3. Telegram-бот: один процесс — много ботов
Сейчас бот регистрирует webhook на старте. Для мульти-арендности:
- Каждый клуб → свой Telegram-бот (свой `BOT_TOKEN`).
- API принимает webhook по пути `/api/bot/webhook/:tenant_slug` (или
  использует `X-Telegram-Bot-Api-Secret-Token` для маршрутизации).
- В админке клуб добавляет свой `BOT_TOKEN` → API регистрирует webhook
  динамически.

#### 2.4. Frontend (Mini App + Admin)
- URL-схема: `https://app.<saas-domain>/<club-slug>` или
  `https://<club-slug>.<saas-domain>`.
- На старте Mini App читает `club-slug` из URL/initData →
  бэкенд резолвит `tenant_id`.
- В Admin — добавить выбор клуба в JWT (если один аккаунт админит несколько клубов).

#### 2.5. Миграция существующих клиентов
- Скрипт миграции: для каждого существующего single-tenant клуба
  заводится `tenant`, проставляется `tenant_id` во все строки,
  данные сливаются в shared-БД.
- Период co-existence: старые single-tenant установки продолжают работать,
  новые клиенты — на SaaS.

**Итог этапа 2:**
- Время установки клуба: **5 минут** (заполнил форму на лендинге → готово).
- Один человек поддерживает 100+ клубов.

---

### Этап 3. SaaS (биллинг + self-service) (3–4 недели)

#### 3.1. Лендинг + регистрация
- Маркетинговая страница: цены, фичи, отзывы.
- Форма регистрации: email, название клуба, slug → создаётся tenant,
  присылается ссылка на админку.
- Trial-период: 14 дней без оплаты.

#### 3.2. Биллинг
- Российский рынок: **ЮKassa** / **CloudPayments** (с фискализацией).
- Зарубежный: Stripe.
- Тарифы: по количеству клиентов / тренеров / занятий в месяц.
- Webhook'и провайдера → API → перевод tenant в `is_active = false` при неоплате.

#### 3.3. Лимиты и квоты
- Лимит занятий/тренеров/клиентов по тарифу.
- Графики использования в админке.

## 5. Что начать делать прямо сейчас (минимальный шаг)

Если бюджет на разработку ограничен, **первая итерация — Этап 1.1 + 1.3 + 1.4**:

1. **`scripts/install.sh`** — превратить `deploy-steps.md` в один скрипт.
   Это даёт мгновенный выигрыш: установка ускоряется в 10–20 раз.
2. **`scripts/backup.sh` + cron** — без бэкапов продавать клубу нельзя.
3. **UptimeRobot + Sentry** — иначе про падения узнаёшь от клиента.

Эти три задачи реально закрыть за неделю и сразу пойти продавать.
Всё остальное — по мере появления клиентов и денег.

## 6. Чек-лист готовности к продаже клубу

Прежде чем брать первого платящего клиента:

- [ ] `install.sh` отрабатывает на чистой Ubuntu 24.04 за < 20 минут.
- [ ] Автобэкапы БД настроены и **протестировано восстановление** на свежей машине.
- [ ] UptimeRobot или аналог следит за `api.*/health`.
- [ ] Sentry собирает ошибки бэка и фронта, проект общий.
- [ ] Подготовлен договор + согласие на обработку ПДн (152-ФЗ).
- [ ] Клиент понимает, что **он** — оператор ПДн своих клиентов
      (или это явно прописано в договоре).
- [ ] Документ для клиента «как пользоваться админкой» (1–2 страницы).
- [ ] Понятна модель передачи доступов: домен/VPS/бот на чьё имя.
- [ ] Прайс зафиксирован: установка, ежемесячная поддержка, доработки.

## 7. Открытые вопросы (требуют решения до Этапа 2)

1. **Single Telegram-бот или per-tenant бот?** Per-tenant — лучше для брендинга
   (бот называется именем клуба), но требует от клиента отдельной регистрации
   в @BotFather. Single — проще онбординг, но Mini App один на всех.
2. **Subdomain (`club.app.com`) vs path (`app.com/club`)?** Subdomain — красивее,
   но усложняет Telegram Mini App (домен в @BotFather один). Path — проще
   технически.
3. **Какой биллинг-провайдер первым?** Зависит от того, на какой рынок
   целишься — РФ или зарубеж.
4. **Где хостить SaaS?** HOSTVDS отлично для single-tenant, но для shared
   стоит посмотреть Selectel/Yandex Cloud с managed Postgres — снимет
   головную боль с бэкапами и репликацией.
