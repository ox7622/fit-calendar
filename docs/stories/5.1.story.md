# Story 5.1: Class Reminder Subscription

## Status

ready-for-dev

## Story

**As a** gym member,
**I want** to subscribe to reminders for specific classes,
**so that** I get notified before classes I plan to attend.

## Acceptance Criteria

1. Class detail view (`ClassDetailPage`) includes a "Remind Me" button (`Напомнить`) below the date/time card.
2. `POST /api/v1/reminders` creates a reminder subscription for the authenticated user + given `scheduleEntryId`.
3. Button toggles to "Cancel Reminder" (`Отменить напоминание`) when an active subscription exists for that class.
4. A user can subscribe to multiple distinct classes (no per-user limit beyond the unique constraint per class).
5. Subscription is linked to the authenticated user (resolved from `X-Telegram-Init-Data` via `TelegramAuthGuard`); never accept `userId` from the client.
6. `DELETE /api/v1/reminders/:id` removes a subscription. Only the owning user can delete their own reminder (404 otherwise).
7. Duplicate `POST` for the same `(userId, scheduleEntryId)` returns the existing reminder with HTTP 200 (idempotent), rather than throwing a 409 from the unique constraint.
8. After successful subscribe/unsubscribe, a toast notification confirms the action. Subscribe toast: "Напомним за N минут" where N = the user's `reminderMinutes`.
9. Cannot subscribe to past classes or classes with `status = 'cancelled'` — return 400 with a Russian error message in the standard error format.
10. New endpoints documented in Swagger and protected by `TelegramAuthGuard` per the existing API pattern.

This is the **first** Epic 5 story. Epics 1–4 are Done/Complete. The relevant existing pieces this story sits on top of:

-   **Authentication**: `TelegramAuthGuard` at `apps/api/src/common/guards/telegram-auth.guard.ts` — every endpoint uses `@UseGuards(TelegramAuthGuard)` and reads the user via the `@TelegramUser()` decorator. See `coaches.controller.ts` for the canonical pattern.
-   **User upsert**: `UserService.upsert()` at `apps/api/src/modules/user/user.service.ts:35` is the only correct way to resolve the current user record from Telegram data. Always go through it — never query by `telegramId` directly in feature modules.
-   **Reminder entity**: Already defined at `libs/db/src/entities/reminder.entity.ts`. Critical details:
    -   `@Unique(['userId', 'scheduleEntryId'])` — DB-level idempotency guard. Catch this if the application-level pre-check loses a race; do not let it surface as 500.
    -   `notifyAt` is precomputed at insert time (not a derived view). If the user later changes `reminderMinutes`, existing reminders keep their original `notifyAt`. This is correct per architecture — Story 5.2 will not retroactively adjust.
    -   `onDelete: 'CASCADE'` on both relations — when a class is deleted or a user is removed, reminders are auto-cleaned.
-   **Frontend detail page**: `apps/mini-app/src/pages/ClassDetailPage.tsx` is where the button lives. Read it end-to-end before editing — it has a careful loading/error/cancelled branching. The button goes inside the success branch, after the date/time card and before the difficulty row. Place it as a full-width primary button.
-   **API client**: `apps/mini-app/src/shared/api/client.ts` already injects `X-Telegram-Init-Data`. Use `apiClient.post`, `apiClient.delete` — do not write a new fetch wrapper.

### Endpoint contracts

**`POST /api/v1/reminders`**

Request body:

```json
{ "scheduleEntryId": "uuid-string" }
```

Response 200 (existing or new):

```json
{
    "id": "reminder-uuid",
    "scheduleEntryId": "schedule-entry-uuid",
    "notifyAt": "2026-05-15T09:30:00.000Z",
    "status": "pending"
}
```

Errors: 400 (cancelled/past class), 401 (no/invalid initData), 404 (schedule entry not found).

**`DELETE /api/v1/reminders/:id`**

Response 204 No Content. Errors: 401, 404 (not found OR not owned by caller — same response for both, no leakage).

### Reminder service core logic

```typescript
async subscribe(telegramData: ITelegramUserData, scheduleEntryId: string): Promise<ReminderResponseDto> {
    const user = await this.userService.upsert(telegramData);

    const entry = await this.scheduleRepo.findOne({ where: { id: scheduleEntryId } });
    if (!entry) throw new NotFoundException('Class not found');
    if (entry.status === 'cancelled') throw new BadRequestException('Занятие отменено');
    if (entry.startTime.getTime() <= Date.now()) throw new BadRequestException('Занятие уже началось');

    const existing = await this.reminderRepo.findOne({
        where: { userId: user.id, scheduleEntryId }
    });
    if (existing) return this.toDto(existing);

    const reminder = this.reminderRepo.create({
        userId: user.id,
        scheduleEntryId,
        notifyAt: subMinutes(entry.startTime, user.reminderMinutes),
        status: 'pending',
    });

    try {
        const saved = await this.reminderRepo.save(reminder);
        return this.toDto(saved);
    } catch (err) {
        // Race: another request inserted between our check and save.
        // Re-fetch and return the winner. Don't throw 500 on the unique violation.
        if (this.isUniqueViolation(err)) {
            const winner = await this.reminderRepo.findOne({
                where: { userId: user.id, scheduleEntryId }
            });
            if (winner) return this.toDto(winner);
        }
        throw err;
    }
}
```

[Source: `libs/db/src/entities/reminder.entity.ts`, architecture.md#Section-4.2]

### Idempotency — why this matters

The PRD-specified idempotency (AC7) is non-trivial. Two requests in flight can both pass the pre-check, then both attempt the insert; one wins, the other hits the unique constraint. The `try/catch` with re-fetch above handles this cleanly. Don't shortcut by using `INSERT ... ON CONFLICT` — TypeORM's repo abstraction is what the rest of the codebase uses; stay consistent.

For `isUniqueViolation`, Postgres throws with `code === '23505'`. TypeORM surfaces this as a `QueryFailedError`. Pattern:

```typescript
private isUniqueViolation(err: unknown): boolean {
    return err instanceof QueryFailedError &&
        (err as QueryFailedError & { code?: string }).code === '23505';
}
```

### What this story does NOT do

-   **No reminder list page yet** — that's Story 5.6. `RemindersPage.tsx` stays as the current placeholder (`apps/mini-app/src/pages/RemindersPage.tsx`).
-   **No actual notification delivery** — that's Story 5.3 (scheduled job + bot send).
-   **No reminder time settings UI** — that's Story 5.2. The user's `reminderMinutes` value already exists on the User record (default 30, set in Story 1.5).
-   **No `GET /reminders` endpoint** — that's Story 5.6. The button on `ClassDetailPage` does not pre-populate its toggle state from the server in 5.1; it only reflects state changes from the user's own actions during the current session. This is acceptable because (a) the only side-effect of an unaware repeat-subscribe is the idempotent return path, and (b) once 5.6 ships the page will pre-fetch.
