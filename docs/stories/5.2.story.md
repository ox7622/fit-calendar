# Story 5.2: Reminder Time Preferences

## Status

Ready for Review

## Story

**As a** gym member,
**I want** to configure how long before a class I receive reminders,
**so that** notifications arrive at a time that works for my schedule.

## Acceptance Criteria

1. Settings UI in the Mini App exposes a single field: "Reminder time" (`Когда напоминать`).
2. Allowed values are exactly `15`, `30`, `60`, `120` minutes — rendered as `"15 минут до"`, `"30 минут до"`, `"1 час до"`, `"2 часа до"`. No other values are accepted by either UI or API.
3. Default for new users is `30` (already enforced by `UserService.upsert` from Story 1.5 — no change needed there).
4. `PUT /api/v1/users/settings` accepts `{ reminderMinutes: 15 | 30 | 60 | 120 }` and updates the authenticated user's preference.
5. `GET /api/v1/users/settings` returns the authenticated user's current preference: `{ reminderMinutes: number }`.
6. After save, the new value is immediately reflected in `useUserStore` so subsequent reminder subscriptions (Story 5.1) compute `notifyAt` from the new preference and the toast confirmation shows the new value.
7. Setting persists across sessions (already true since it's stored on the User row — verify by closing/reopening the Mini App).
8. Existing reminders are NOT retroactively re-scheduled when the preference changes. New `notifyAt` values apply only to reminders created **after** the change. (See Story 5.1 dev notes — `notifyAt` is precomputed, not derived.)
9. Both endpoints protected by `TelegramAuthGuard`. Validation errors return 400 with the standard error format. Unknown/invalid values must be rejected.

Either way works. Sequence 7.2 → 5.2 if possible.

### What's already built

This story is mostly UI on top of existing primitives:

-   `User.reminderMinutes` field exists with default 30 (`libs/db/src/entities/user.entity.ts`, set up in Story 1.2)
-   `UserService.upsert()` creates new users with `reminderMinutes: 30` (`user.service.ts:54`)

-   `UserDto` already exposes `reminderMinutes` (`dto/user.dto.ts:20`); `/users/me` returns it
-   `useUserStore` already holds `user.reminderMinutes` from the `/users/me` response (`apps/mini-app/src/shared/stores/userStore.ts`)
-   `TelegramAuthGuard` + `@TelegramUser()` decorator pattern (Story 1.5)

What's actually new:

-   The two `/users/settings` endpoints (controller wiring + DTOs)
-   The validation constraint to the 4 allowed values
-   The Settings sheet UI

### Why the gear icon goes on `RemindersPage`

The bottom nav has 4 tabs already (Schedule/Coaches/Reminders/Club) and the Telegram Mini App layout doesn't have headroom for a 5th. The PRD-listed front-end-spec §2.2 mentions "Settings" as accessible from a hamburger menu or profile icon — neither exists in the current shell.

For MVP, settings is **reminder-time-only**. Putting it on `RemindersPage` is the most contextually correct home: a user thinking about reminders is the user who needs to adjust this setting. When a second setting category appears, promote it to a separate `/settings` route then.

If the dev disagrees and wants a `/settings` route from day one, that's a defensible choice — but please don't add a 5th bottom tab.

### Why a sheet, not a route

One field = one sheet. The existing `FilterSheet` pattern (`apps/mini-app/src/components/FilterSheet.tsx`) is the visual template — match its slide-up animation, backdrop, rounded-top corners, and chip-style selection. Reusing the established pattern keeps the app feeling cohesive.

### Validation — defense in depth

PRD ACs say "Options: 15/30/60/120." That's a UX statement, but the API must enforce it too. A determined client could `PUT { reminderMinutes: 99999 }` and break Story 5.3's notification scheduling logic. Two layers:

1. **DTO**: `class-validator`'s `@IsIn(REMINDER_MINUTES_OPTIONS)` rejects bad values at the boundary
2. **App-level pipes**: already configured globally in `main.ts:35-49` with `whitelist + forbidNonWhitelisted` — no work needed beyond declaring the DTO

```typescript
// dto/settings.dto.ts
import { ApiProperty } from '@nestjs/swagger';
import { IsIn } from 'class-validator';
import { REMINDER_MINUTES_OPTIONS } from '../user.constants';

export class UpdateSettingsDto {
    @ApiProperty({ enum: REMINDER_MINUTES_OPTIONS, example: 30 })
    @IsIn(REMINDER_MINUTES_OPTIONS as unknown as number[])
    reminderMinutes: number;
}

export class SettingsResponseDto {
    @ApiProperty({ example: 30 })
    reminderMinutes: number;
}
```

### Endpoint contracts

**`GET /api/v1/users/settings`** → `200 { "reminderMinutes": 30 }`

**`PUT /api/v1/users/settings`**

Request: `{ "reminderMinutes": 60 }`
Response 200: `{ "reminderMinutes": 60 }`
Errors: 400 (invalid value or extra fields), 401 (no/invalid initData)

### Why the sheet pulls from the store, not the GET endpoint

`/users/me` already populates `useUserStore.user.reminderMinutes` during auth (Story 1.5). Re-fetching `/users/settings` on sheet-open is a redundant network round-trip. The PRD AC requires the GET endpoint to exist (and Story 5.6 may use it), but the UI itself doesn't need it.

### Coupling with Story 5.1 — important

If 5.1 is implemented before this story (recommended order), the toast text "Напомним за {user.reminderMinutes} минут" pulls from the store. As long as Task 9 (the `setReminderMinutes` Zustand action) updates the store on save, subsequent reminder subscriptions in the same session will use the new value.

If 5.1 is NOT yet implemented when this is built, no integration concern — the field just sits on the User record waiting.

### Zustand store update

```typescript
// apps/mini-app/src/shared/stores/userStore.ts (add to existing store)
interface UserState {
    // ... existing fields
    setReminderMinutes: (minutes: number) => void;
}

export const useUserStore = create<UserState>((set) => ({
    // ... existing
    setReminderMinutes: (minutes) =>
        set((state) => ({
            user: state.user ? { ...state.user, reminderMinutes: minutes } : null,
        })),
}));
```
