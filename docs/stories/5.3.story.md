# Story 5.3: Reminder Notification Delivery

## Status

Ready for Review

## Story

**As a** gym member,
**I want** to receive a Telegram message before my subscribed classes,
**so that** I have time to prepare and get to the gym.

## Acceptance Criteria

1. A scheduled job runs every minute on the API and processes due reminders.
2. A reminder is "due" when `status = 'pending'` AND `notifyAt <= now()`.
3. For each due reminder, the bot sends a Telegram message to the user (private chat with the user's `telegramId`).
4. Message body (Russian) includes the class name, start time (`HH:mm`), and coach name. Format below in Dev Notes.
5. Message includes a deep-link button (`web_app` inline keyboard) that opens the Mini App at `/schedule/:classId`.
6. On successful send: reminder status transitions to `'sent'`, `sentAt = now()`.
7. On failed send: retry up to 3 attempts total (1 initial + up to 2 retries on subsequent cron ticks). After 3 failures, status transitions to `'failed'` and the reminder is no longer attempted.
8. Each failed attempt is logged with `reminderId`, attempt number, error message, and the Telegram error code (if available).
9. A reminder is sent at most once — the cron job MUST NOT duplicate sends if a tick takes longer than expected.
10. The cron job is resilient: an exception while processing one reminder must not abort the batch. Other due reminders in the same tick still attempt.

## Dev Notes

### Why this story is more involved than 5.1/5.2/5.6

5.3 is the only Epic 5 story that introduces:

1. A new dependency (`@nestjs/schedule`)
2. A migration (new column on the `reminders` table)
3. Cross-module coordination (Reminder ↔ Bot)
4. Background processing semantics (single-flight, retry, partial failure)

Treat it as a foundation piece — once the dispatcher pattern is established, Stories 5.4 and 5.5 (cancellation/change notifications) can reuse the same `BotService.sendNotification` method but trigger synchronously from admin actions instead of from cron.

### Message format

Russian, HTML parse mode (use `parse_mode: 'HTML'` in grammY):

```
🔔 <b>Напоминание о занятии</b>

<b>Йога для начинающих</b>
🕘 Сегодня в 10:00
👤 Тренер: Мария Иванова
```

Followed by an inline keyboard with the single button `📅 Открыть` (web_app deep link to `/schedule/:classId`).

The message timing-text logic:

-   If the class is today → `Сегодня в HH:mm`
-   If the class is tomorrow → `Завтра в HH:mm`
-   Otherwise (uncommon — only if user's `reminderMinutes >= 24h*60`) → `d MMMM в HH:mm`

Use `date-fns` with the `ru` locale (already used in `ClassDetailPage.tsx`).

### Why retryCount over a separate attempts table

The PRD says "max 3 attempts" — that's all the granularity we need. A standalone `reminder_send_attempts` table would be over-engineered for MVP. The single integer column is enough; if we later need per-attempt error history we can add it then. (Story 5.4/5.5 won't need it — they're synchronous, not retried.)

### Single-flight lock — why an in-memory boolean is enough for MVP

The brief notes hosting is TBD. The MVP-ready answer for a single instance is:

```typescript
@Cron(CronExpression.EVERY_MINUTE)
async processDueReminders(): Promise<void> {
    if (this.isProcessing) {
        this.logger.warn('Previous tick still in flight; skipping');
        return;
    }
    this.isProcessing = true;
    try {
        const due = await this.reminderService.findDueReminders();
        await pLimit(5)(due.map((r) => () => this.processOne(r)));
    } finally {
        this.isProcessing = false;
    }
}
```

The `try/finally` is important: an unhandled throw must release the lock or the dispatcher gets stuck for the lifetime of the process.

For multi-instance, this falls apart immediately (each replica thinks it has the lock). The Task 11 comment flags this loudly.

### Why the dispatcher is in the Reminder module, not the Bot module

The Bot module is for inbound Telegram updates (webhook) and command handlers. The dispatcher is outbound, scheduled, and reminder-domain — so it lives with the rest of the reminder code. The dispatcher _uses_ the bot to send, the same way the user.controller uses the user.service to query.

If you find yourself adding non-reminder scheduled jobs (e.g. periodic schedule sync), don't put them in the reminder module — that's how reminder.module becomes a god-module. Add a separate scheduling module then.

### Telegram rate limits — flag for monitoring

Telegram allows ~30 messages per second to different chats and ~1 message per second to a single chat. For MVP volume (~100 active users, sparse reminders) this is far below the limit. But:

-   If a single class has 50+ reminders all firing at the same minute, you can hit the per-chat-group rate limit. (Not our case yet — only direct chats.)
-   Future Story 5.4/5.5 broadcast-style notifications could plausibly trip the global rate limit if the club has many subscribers.

For MVP, no rate limiting in our code. If you see `429 Too Many Requests` from Telegram in logs, that's the signal to introduce a queue with backoff. Don't pre-build it.

### Endpoint contracts

This story has **no new API endpoints**. The dispatcher runs internally on a cron schedule.

If a debug/admin trigger would be helpful during development (e.g. `POST /admin/reminders/process-now`), that belongs in Epic 6, not here.

### Failure modes and observability

-   Telegram returns 403 ("bot was blocked by user") → log and mark `failed` (don't retry — it'll never succeed). This is a useful early refinement: if `error.error_code === 403` (grammY exposes it on `GrammyError`), short-circuit retries.
-   Telegram 5xx → retry path (current logic handles)
-   Network errors → retry path
-   Our DB errors during the status update → log loudly; the reminder will re-fire next tick (same `pending` status) which means the user gets a duplicate. This is a small risk; document it but don't fix in MVP.
