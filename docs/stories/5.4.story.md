# Story 5.4: Schedule Change Notifications

## Status

Ready for Review

## Story

**As a** gym member,
**I want** to be notified when a class I'm subscribed to changes time or details,
**so that** I can adjust my plans accordingly.

## Acceptance Criteria

1. When an admin updates a class's `startTime` or `durationMinutes` (Story 6.3), every subscriber to that class (i.e. user with a `pending` reminder) receives a Telegram message immediately.
2. The message clearly indicates this is a **change** notification, not a routine reminder.
3. The message includes the class name, the **old** time, the **new** time, and the coach name.
4. The message includes a deep-link button to the updated class details (`/schedule/:classId`).
5. Notifications are sent **immediately** (synchronously, in response to the schedule.changed event), not queued for the next reminder cron tick.
6. Failed sends are retried up to 3 times with exponential backoff (e.g., 1s, 5s, 30s), then logged as failed and dropped — they do NOT pollute the `Reminder.status` field (which is reserved for the original reminder lifecycle, not change notifications).
7. The pre-existing reminders' `notifyAt` values were already recomputed by Story 6.3's update handler — this story only handles the change-notification side-effect.
8. Edits that don't shift `startTime` or `durationMinutes` (e.g., admin fixes a typo in coach name — though that's not currently editable) do NOT fire a change notification. The `SCHEDULE_CHANGED_EVENT` from 6.3 only emits on real time changes (per its definition).

## Dev Notes

### Why a listener, not a polling job

Cron-based delivery (Story 5.3) is right for "the time has come, send the reminder now." Change notifications are different: the trigger is an admin action, not the passage of time. Reactive event handling is the natural fit, and means the user gets the news in seconds rather than waiting for the next minute tick.

### Why retry without DB persistence

Unlike the original reminder (which uses `Reminder.status` and `retryCount` to track its lifecycle across restarts), change notifications are ephemeral. If the API restarts mid-retry, the user just doesn't get the notification — they'll see the new time when they check the schedule, and the original reminder will fire at the new computed time. Acceptable degradation for MVP.

If we later want durable change-notification delivery, we'd write to a `notification_log` table or push onto a queue. Not now.

### Coupling with 6.3's reminder recomputation

Story 6.3 already does:

1. Update class
2. Recompute pending reminders' `notifyAt` based on new startTime
3. Emit `SCHEDULE_CHANGED_EVENT`

This story consumes step 3. The reminder recomputation in step 2 is what makes the original cron-based reminder fire at the right time. This change-notification is the "in addition to" feature that warns the user _now_ about the shift.

### Why bail out on cancelled state (Task 6)

A subtle race: admin edits a class, then immediately cancels it. With synchronous post-commit event emission, the change event fires first. By the time our listener loads the class for the message snapshot, status could be `cancelled`. Sending a "this class moved!" message for a class that's actually cancelled is confusing.

The listener checks `status === 'cancelled'` after load and bails. Story 5.5's cancellation listener will fire next from the same admin's cancel action, and the user gets the correct message.

### Endpoint contract

This story has **no new endpoints**. The trigger is an event emitted by Story 6.3's `PUT /admin/schedule/:id`.
