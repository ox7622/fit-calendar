# Story 5.5: Class Cancellation Notifications

## Status

Ready for Review

## Story

**As a** gym member,
**I want** to be notified immediately when a class I'm subscribed to is cancelled,
**so that** I don't waste time going to the gym for nothing.

## Acceptance Criteria

1. When an admin cancels a class (Story 6.4), every user who had a `pending` reminder for that class — captured in the event's `affectedUserIds` — receives a Telegram message immediately.
2. The message clearly indicates this is a **cancellation**, not a routine reminder or a change notification.
3. The message includes the class name, the original date/time, and the cancellation reason if one was provided.
4. Story 6.4 already deletes the underlying pending reminders as part of the cancel transaction, so there is **no separate reminder cleanup work in this story**.
5. Notifications fire immediately (synchronously, in response to the `schedule.cancelled` event), with the same retry/backoff approach as Story 5.4.
6. The event payload contains `affectedUserIds: string[]` (User UUIDs) plus a `snapshot` of class details — this story uses both.
7. Optionally, the message suggests alternative classes on the same day (PRD AC6 for 5.5). For MVP, this is a stretch goal — implement only if the schedule lookup is trivial; otherwise ship without and add a TODO.

## Dev Notes

### Why this story is the simplest of Epic 5's tail

By the time you reach 5.5, all the load-bearing infrastructure exists:

-   `BotService.sendNotification` (5.3)
-   Retry helper (5.4)
-   Event emitter (6.3)
-   `SCHEDULE_CANCELLED_EVENT` and the snapshot payload (6.4)
-   `affectedUserIds` already captured **before** reminder deletion (6.4 Task 6 ensures the order)

Implementation is essentially: subscribe to event, format message, send to each user. Most of the work is the test coverage.

### Why we don't need to load the class for the message

Story 5.4's listener has to load the class to get its name/coach because the change-event payload only carries delta times. Story 6.4's cancellation event was deliberately designed to include a `snapshot` with `className`, `startTime`, `coachName` so this listener doesn't need a DB roundtrip. **Use the snapshot directly.**

If you find yourself wanting to query the class for some other reason here, stop and ask why — the snapshot is the contract.

### Why deep-linking to the cancelled class is wrong

Cancelled classes appear with a strikethrough in the schedule view, and the detail page shows the cancelled banner. A button labeled "Открыть" pointing to a cancelled state is a bad UX. Either omit the button entirely (chosen) or have it link to `/` (today's schedule) so the user can find an alternative.

For MVP, simpler = better. Skip the button.

### Stretch: alternative classes (AC7)

PRD says "Notification suggests alternative classes (same day, if available)." This is genuinely nice but easy to over-engineer. The three lines worth it:

```typescript
const sameDayAlternatives = await this.scheduleRepo.find({
    where: {
        startTime: Between(startOfDay(snapshot.startTime), endOfDay(snapshot.startTime)),
        status: 'scheduled',
        id: Not(payload.scheduleEntryId),
    },
    relations: ['trainingType', 'coach'],
    take: 3,
});
```

If the suggested class list returns empty or fails, just skip the suggestion section — don't fail the notification. This is genuinely a 30-minute add-on if the dev's in the zone; punt to a follow-up if not.
