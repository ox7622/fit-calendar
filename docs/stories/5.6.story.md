# Story 5.6: My Reminders List

## Status

ready-for-dev

## Story

**As a** gym member,
**I want** to see a list of all classes I've subscribed to reminders for,
**so that** I can manage my upcoming workout plans.

## Acceptance Criteria

1. `GET /api/v1/reminders` returns the authenticated user's active reminder subscriptions, sorted by class `startTime` ASC (soonest first).
2. The endpoint excludes reminders whose associated class `startTime` is in the past — past classes never appear in the list.
3. Each list item shows: class name, date + time, coach name, and a "Cancel" affordance.
4. `RemindersPage` renders the list, replacing the current placeholder empty state.
5. Loading skeleton (3 rows) is shown while fetching.
6. Empty state — when the user has zero active reminders — shows a friendly message: `"У вас пока нет напоминаний"` with a sub-line `"Откройте занятие и нажмите 'Напомнить'"`.
7. Error state with retry button shown if the fetch fails.
8. Tapping "Cancel" on a reminder calls `DELETE /api/v1/reminders/:id` (Story 5.1 endpoint), removes the row optimistically, and shows a toast `"Напоминание отменено"`. On API failure, the row is restored and an error toast appears.
9. Tapping the body of a reminder row navigates to the corresponding class detail page (`/schedule/:scheduleEntryId`).
10. The list pre-populates `ClassDetailPage`'s subscription state — when the user opens a class they have a reminder for, the button correctly renders as "Cancel Reminder" (closes the gap noted in Story 5.1 Task 7).

## Dev Notes

### Cross-story dependency — Story 7.2 (auth refactor)

Story 7.2 renames `User` → `Customer` and changes auth to require linking. This story's `GET /reminders` endpoint and the `useRemindersStore` need:

-   **If 7.2 ships first** (recommended): `@Customer()` decorator + `RequiresLinkedCustomer` guard. Reminder rows reference `customerId`, not `userId`. The `loadReminders()` call from `AuthProvider` should only fire when `customer !== null` (post-link), not on every auth.
-   **If 5.6 ships first**: the draft as-written (`userId`, no linked-customer gating) works; expect rework when 7.2 lands.

Either way works. Sequence 7.2 → 5.6 if possible.

### Where this fits

5.6 closes the loop on the user-facing reminder UX:

-   5.1 created the subscription mechanism
-   5.2 lets the user choose the reminder offset
-   **5.6 (this) shows them the list and lets them cancel from one place + closes the toggle-state gap that 5.1 deliberately left open**
-   5.3 will deliver the actual notifications

### The ClassDetailPage gap from 5.1

Story 5.1 Task 7 explicitly noted that the button's initial state is `null` (defaults to "Remind Me") with no pre-fetch — because there was no `GET /reminders` endpoint yet. **This story closes that gap (AC10).** The dev should expect to revisit `ClassDetailPage` and refactor it to read from the new `useRemindersStore` instead of local state.

If the dev landing this story finds 5.1 **not yet shipped**, they should still build the GET endpoint, the page, and the store, but they may skip Task 9-10's `ClassDetailPage` integration and leave it for whoever lands 5.1.

### Why a reminders store

The same data is read by two places:

-   `RemindersPage` (the whole list)
-   `ClassDetailPage` (one item lookup by `scheduleEntryId`)

Without a store, every detail-page open would either accept a stale state or do an extra `GET /reminders` round-trip. With a store loaded once on auth, both consumers share the same source of truth and stay in sync after mutations.

The store is per-session — it doesn't need to persist to localStorage. On re-open, auth runs and `loadReminders()` re-fires.

### Endpoint contract

**`GET /api/v1/reminders`** → `200`

```json
[
    {
        "id": "reminder-uuid",
        "scheduleEntryId": "class-uuid",
        "status": "pending",
        "notifyAt": "2026-05-15T09:30:00.000Z",
        "class": {
            "id": "class-uuid",
            "name": "Йога для начинающих",
            "startTime": "2026-05-15T10:00:00.000Z",
            "durationMinutes": 60,
            "coachName": "Мария Иванова",
            "coachPhotoUrl": "https://..."
        }
    }
]
```

Errors: 401 (no/invalid initData). Empty array (not 404) when user has no reminders.

### Service query

```typescript
async findActiveByUser(telegramData: ITelegramUserData): Promise<ReminderListItemDto[]> {
    const user = await this.userService.upsert(telegramData);
    const now = new Date();

    const reminders = await this.reminderRepo
        .createQueryBuilder('r')
        .innerJoinAndSelect('r.scheduleEntry', 'entry')
        .innerJoinAndSelect('entry.coach', 'coach')
        .innerJoinAndSelect('entry.trainingType', 'type')
        .where('r.userId = :userId', { userId: user.id })
        .andWhere('entry.startTime > :now', { now })
        .orderBy('entry.startTime', 'ASC')
        .getMany();

    return reminders.map((r) => this.toListItemDto(r));
}
```

The `createQueryBuilder` form is preferred over `find({ where, relations })` here because the `startTime > now` filter is on a related table — possible with `find` but uglier.

**Note:** if Story 6.2 has already shipped, `createQueryBuilder` is established in the codebase. If not, this story (or 6.2 — whichever lands first) is the first to use it. The existing pattern everywhere else is `repository.find({ where, relations })` — see `apps/api/src/modules/coaches/coaches.service.ts`. Don't fall back to that pattern here; the related-table filter genuinely needs the query builder.

### "Past classes excluded" — automatic but worth re-verifying after 5.3

AC2 filters past classes server-side. Once Story 5.3 (delivery) ships, sent reminders will have `status='sent'` but the underlying class will eventually be in the past — at which point this filter still excludes them. So the list is naturally self-pruning without any cleanup job. The dev should NOT add a separate "completed reminders" view for MVP.
