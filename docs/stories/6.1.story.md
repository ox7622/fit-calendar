# Story 6.1: Admin Authentication

## Status

Ready for Review

## Story

**As a** club administrator,
**I want** to securely log in to the admin panel,
**so that** only authorized staff can manage club content.

## Acceptance Criteria

1. Admin panel is served at `/admin` (or as a separate app at port 4010 in dev) with a dedicated login page.
2. Login form accepts email + password and submits to `POST /api/admin/auth/login`.
3. Passwords are verified against `AdminUser.passwordHash` using `bcrypt.compare`. Hashes are bcrypt with min 10 rounds (already produced by the seed script).
4. On success: API returns a signed JWT (HS256) with `{ sub: adminUserId, email, name }` claims, expiring in 24 hours. The Admin app stores the token in `localStorage` and redirects to `/admin/dashboard`.
5. `AdminUser.lastLoginAt` is updated on every successful login.
6. Failed logins (wrong email, wrong password, or `isActive=false`) return a generic 401 with the same message — no user enumeration leakage. UI shows a single Russian message: `"Неверный email или пароль"`.
7. JWT is sent in the `Authorization: Bearer <token>` header on every subsequent admin API request.
8. A NestJS guard (`AdminAuthGuard`) protects all `/admin/*` API routes (except the login endpoint itself). On invalid/missing/expired token: 401.
9. Admin app has a route guard that redirects unauthenticated users from any protected page to `/admin/login`.
10. Logout button clears the localStorage token and redirects to `/admin/login`. Server-side blacklist is **not** required for MVP (stateless JWT — 24h expiry is the bound).
11. The login endpoint is rate-limited (max 5 attempts per IP per 15 minutes) to slow brute force.
12. `JWT_SECRET` is required in env validation; the API refuses to boot without it.

### JWT — passport vs raw verifyAsync

The mini-app side uses a hand-rolled `TelegramAuthGuard` — no passport. For consistency and minimum dep weight, **don't introduce `@nestjs/passport` for admin auth**. Use `@nestjs/jwt` directly.

Compact guard skeleton:

```typescript
@Injectable()
export class AdminAuthGuard implements CanActivate {
    constructor(private readonly jwt: JwtService, private readonly config: ConfigService) {}

    async canActivate(ctx: ExecutionContext): Promise<boolean> {
        const req = ctx.switchToHttp().getRequest<Request>();
        const auth = req.headers['authorization'];
        if (!auth?.startsWith('Bearer ')) throw new UnauthorizedException();

        const token = auth.slice(7);
        try {
            const payload = await this.jwt.verifyAsync<{ sub: string; email: string; name: string }>(token, {
                secret: this.config.getOrThrow('JWT_SECRET'),
            });
            req.admin = { id: payload.sub, email: payload.email, name: payload.name };
            return true;
        } catch {
            throw new UnauthorizedException();
        }
    }
}
```

Mirrors Story 1.5's `TelegramAuthGuard` shape — same try/catch unification of all failure modes into 401.

### Login endpoint contract

**`POST /api/admin/auth/login`**

Request:

```json
{ "email": "admin@fitcalendar.ru", "password": "admin123" }
```

Response 200:

```json
{
    "token": "eyJhbGc...",
    "admin": { "id": "uuid", "email": "admin@fitcalendar.ru", "name": "Admin" }
}
```

Errors: 401 (bad creds; same message regardless of which field), 429 (rate limit hit), 400 (validation — empty fields, invalid email format).

### Rate limiting — single throttle target is enough

PRD AC11 specifies "max 5 attempts per IP per 15 minutes." `@nestjs/throttler` does this out of the box with the per-route `@Throttle` decorator on the login handler. Use IP-based default key (the lib's default).

The global throttle (Task 6) is a separate concern (general API DDOS protection, per arch §15.1); both can coexist. The decorator-level rule wins for the specific route.

### Why localStorage and not httpOnly cookies

httpOnly cookies are more secure against XSS but require server-controlled session state and CSRF protection. For an MVP single-tenant admin panel:

-   `localStorage` is acceptable
-   The mini-app side already uses `localStorage` for `initData` indirectly (via Telegram WebApp SDK)
-   24h expiry bounds the blast radius

If we later expose the admin app over the public internet to many tenants, revisit.

### Token revocation — why MVP doesn't need it

Stateless JWT means we can't "logout" a token from the server side. For MVP this is fine: 24h max compromise window, single tenant, ~1-3 admins. If a token is compromised, rotate `JWT_SECRET` (invalidates all admin sessions globally — acceptable nuclear option).

If/when admin count grows, introduce a `revoked_tokens` table or switch to opaque session tokens.

### PRD divergence — hard 24h vs sliding inactivity expiry

PRD AC6 reads "Session expires after 24 hours of **inactivity**" — i.e. a sliding window where activity refreshes the timer. This story implements a **hard 24h from issue** (no refresh on activity).

Reasons for the divergence:

-   Sliding sessions require a refresh-token pattern (or server-side session tracking). Both are meaningful additional complexity.
-   For ~1-3 admins doing back-office work, hitting the 24h boundary is a one-click re-login. Not a real UX problem.
-   Tighter expiry (a hard cap) is _more_ secure than a sliding session that could remain valid indefinitely if the admin keeps the tab open.

If the user pushes back and wants true sliding inactivity expiry, the cleanest add-on is: introduce a refresh token endpoint (`POST /admin/auth/refresh`) that validates the current token, issues a new one with a fresh 24h window, and the frontend calls it on each user action. This is a well-bounded follow-up story — don't smuggle it into 6.1.

### Seeded admin

The seed script creates `admin@fitcalendar.ru` with the password `admin123`, but the current bcrypt hash in `libs/db/src/seeds/seed.ts` is a placeholder (see Task 14). Once Task 14 replaces it with a real hash, the dev can log in immediately after `pnpm db:seed`. **Document the credentials in `apps/admin/README.md` (create if missing)** — the next person picking up Epic 6 should not have to grep the seed script to find them.

**Reminder:** the placeholder hash is the kind of thing that's been sitting in the codebase since Story 1.2 and only matters once auth is wired. Now that we're wiring auth, Task 14 closes the gap.

**Mid-Task 2 — Repo typecheck fix (out of original story scope, accepted by PO during Task 2)**

Investigated `TS2688: Cannot find type definition file for '@nx/react/typings/cssmodule.d.ts' / image.d.ts / vite/client` (reproduced on both `admin` and `mini-app`).

Root cause: two latent bugs in the existing tsconfig pattern, neither introduced by this story:

1. `tsconfig.base.json` sets `"moduleResolution": "node"` (legacy classic). Classic node resolution does not honor a package's `exports` map. Vite exposes its client types via `exports["./client"]` (`node_modules/vite/client.d.ts`), so `vite/client` couldn't be resolved.
2. `tsconfig.app.json` listed file paths inside packages (`@nx/react/typings/cssmodule.d.ts`, `image.d.ts`) in `compilerOptions.types`. That field expects type-package _names_, not file paths — the lookup tries to find a folder named `cssmodule.d.ts` containing an `index.d.ts`, which never matches. Older Nx generators emitted this; modern resolver doesn't accept it.

Why the breakage was invisible until now: Vite uses esbuild for transpilation, not `tsc`. The `typecheck` target was the only consumer and apparently didn't run in CI.

Fix per app (admin + mini-app, identical pattern):

-   `tsconfig.app.json`: drop the file-path entries from `types`, set `"moduleResolution": "bundler"` and `"module": "esnext"` (bundler requires ES module). For mini-app, also add `"baseUrl": "."` + `"paths": { "@/*": ["src/*"] }` to mirror the alias already in `vite.config.ts`.
-   `src/vite-env.d.ts` (new in both apps): `/// <reference types="vite/client" />` — vite's own client types redeclare `*.module.css`, `*.svg`, `*.png`, etc., so the `@nx/react/typings/*` entries become redundant. Plus a global `declare global { namespace JSX { ... = ReactJSX.* } }` augmentation, because `@types/react@19.0.0` removed the global `JSX` namespace and ~20 existing `JSX.Element` annotations in mini-app source would otherwise need per-file edits.

Side benefit: ~70 cascading errors in mini-app source (implicit-any in callbacks, missing `@/shared/api` modules) were all phantom — they vanished as soon as the path alias resolved. No real source-level type bugs in mini-app after the config fix.

Files touched outside `apps/admin` are listed in the File List under **mini-app typecheck fix**.
