# Story 6.3: Schedule Management - Create & Edit Classes

## Status

Ready for Review

## Story

**As a** club administrator,
**I want** to add new classes and edit existing ones,
**so that** I can keep the schedule up to date.

## Acceptance Criteria

1. `POST /api/v1/admin/schedule` creates a new class with `{ trainingTypeId, coachId, startTime, durationMinutes }`. Returns 201 + the created entry.
2. `PUT /api/v1/admin/schedule/:id` updates an existing class. Same fields are editable. Returns 200 + the updated entry.
3. `GET /api/v1/admin/schedule/:id` returns a single class for the edit form to populate.
4. `durationMinutes` allowed values are exactly `30`, `45`, `60`, `90` (matches PRD AC7 of the original story). Other values are rejected with 400.
5. `startTime` must be a valid ISO datetime. The API does not enforce future-only — admins may legitimately log a past class for record-keeping. (Frontend can warn, server doesn't block.)
6. `trainingTypeId` must reference an existing, **active** training type; `coachId` must reference an existing, **active** coach. Otherwise 400.
7. **PUT does NOT change `status`** — cancellation goes through Story 6.4's dedicated endpoint to ensure the cancellation-notification side-effect runs.
8. **PUT triggers a "schedule changed" event** when `startTime` or `durationMinutes` changes. The event payload includes `{ scheduleEntryId, oldStartTime, newStartTime, oldDurationMinutes, newDurationMinutes }` so Story 5.4's listener can notify subscribers.
9. **If `startTime` changes on PUT, every existing pending reminder for that class has its `notifyAt` recomputed** based on each subscribing user's `reminderMinutes`. This keeps reminders aligned with the new class time.
10. Both endpoints protected by `AdminAuthGuard`.
11. Admin "Add Class" page (`/admin/schedule/new`) and "Edit Class" page (`/admin/schedule/:id`) provide forms with the four fields plus Save/Cancel.
12. Form validation matches the API: training type and coach selected from dropdowns of active records, duration is a 4-option select, datetime via native `<input type="datetime-local">`.
13. On save: success toast `"Сохранено"`, navigate back to dashboard. On error: keep form state, show error message.

## Dev Notes

### Why this story carefully separates create/edit from cancel

Cancellation has a notification side-effect (Story 5.5) and removes pending reminders. Edit has a different notification side-effect (5.4) and _recomputes_ reminders. Conflating them in a single endpoint with `status` updates would force the admin to remember a separate flow for each — and a bug in either branch would cross-contaminate. Two endpoints, two side-effect contracts.

### The `EventEmitter` choice

NestJS's `EventEmitter2` (from `@nestjs/event-emitter`) is the right granularity here:

-   **Why not direct injection of ReminderService?** Couples admin module to reminder module. Story 5.4 doesn't yet exist — and might not, if the user de-scopes. Decoupling via events lets each module own its own concerns.
-   **Why not a real message queue (BullMQ, etc)?** Way too heavy for in-process synchronous side-effects. The whole admin save happens in a single request — no need for durable queues.

The recomputation of reminders (Task 4) is **synchronous and inline**, NOT event-driven. It must complete before the response returns, because the admin would expect their save to leave the system in a consistent state. The event is for the **notification** side-effect (out-of-band) — that one can be async.

### Recompute math

```typescript
// reminder.service.ts (new method)
async recomputeNotifyAtForClass(scheduleEntryId: string, newStartTime: Date): Promise<void> {
    const reminders = await this.reminderRepo.find({
        where: { scheduleEntryId, status: 'pending' },
        relations: ['user'],
    });

    await Promise.all(
        reminders.map((r) =>
            this.reminderRepo.update(r.id, {
                notifyAt: subMinutes(newStartTime, r.user.reminderMinutes),
            })
        )
    );
}
```

A single-statement bulk UPDATE with a SQL expression would be more efficient, but for MVP volumes (low tens of reminders per class) the row-by-row update is clearer and unmissable in code review. Premature optimization is a real cost here.

**Partial-failure mode:** if `Promise.all` rejects partway, some reminders have the new `notifyAt` and others still have the old value. The schedule update has already committed (it ran before this method). Per Task 4's instruction, log the failure and don't fail the admin's save — this leaves the system in an eventually-consistent state where some users get reminders at the new time and others at the old. For MVP this is acceptable; logging surfaces the case so it's visible. The proper fix (transactional with the schedule update, or a retry queue) is post-MVP.

### What the form does NOT do

-   No "recurring class" support (Phase 2)
-   No conflict detection (e.g. "this coach is already teaching at this time" — admin's responsibility for MVP)
-   No drag-to-reschedule on the calendar view
-   No bulk actions

If the dev finds themselves building any of these, stop and raise it.

### Endpoint contracts

**`POST /api/v1/admin/schedule`** body:

```json
{
    "trainingTypeId": "uuid",
    "coachId": "uuid",
    "startTime": "2026-05-04T08:00:00.000Z",
    "durationMinutes": 60
}
```

→ 201 with the created entry (same shape as 6.2 list item).

**`PUT /api/v1/admin/schedule/:id`** — same body, all four fields. Status is read-only via this endpoint. → 200 with the updated entry.

**`GET /api/v1/admin/schedule/:id`** → 200 with the single entry.

Errors: 400 (validation, inactive coach/type), 401 (no/invalid token), 404 (PUT/GET on non-existent id).

### Completion Notes List

- **Customer model adapted from story draft's User refs**: `recomputeNotifyAtForClass` joins `reminder.customer` (not `reminder.user` per the v1.x draft) and reads `customer.reminderMinutes`. The Reminder entity's FK was already `customerId` after 7.2, so the query change is mechanical.
- **Event payload is the contract for Story 5.4**: `SCHEDULE_CHANGED_EVENT` + `IScheduleChangedPayload` exported from `apps/api/src/modules/admin/schedule/schedule.events.ts`. Same file also pre-declares `SCHEDULE_CANCELLED_EVENT` + `IScheduleCancelledPayload` so 6.4 (next) lands cleanly without a separate constants file.
- **Update flow side-effects, in order**: validate coach/trainingType (if changed) → mutate entity → save → recompute reminders (if startTime changed, synchronous) → emit event (if startTime OR durationMinutes changed) → reload + return DTO. Reminder recompute is wrapped in try/catch — admin's save commits regardless. This matches the story's documented partial-failure mode.
- **PUT does not change status**: the DTO doesn't include `status`, and the global `forbidNonWhitelisted: true` 400s a stray `status` field. Cancellation is its own endpoint in 6.4.
- **Recompute is row-by-row**: Promise.all over `repo.update` calls, one per pending reminder. MVP volumes don't justify the readability cost of a single bulk SQL with conditional expressions per row. Documented in the service JSDoc.
- **Frontend dropdowns deferred to 6.5/6.6**: the form uses text inputs for `trainingTypeId` and `coachId` with explicit "будет заменено выпадающим списком в 6.X" helper text. The admin can copy UUIDs from the dashboard list (right-click → inspect) or seed for testing. TODO comment at the top of `ScheduleForm.tsx` flags the hook-up point.
- **datetime-local timezone caveat**: the HTML5 `datetime-local` input has no timezone. The form interprets the value as the admin's local TZ and serializes via `new Date(value).toISOString()` (UTC). The DB column is `TIMESTAMP WITH TIME ZONE`. This is correct for an admin in a single timezone (Russian club). Multi-timezone admin operation would require an explicit TZ picker — out of MVP scope.
- **Reload after save**: both `create` and `update` reload via `findOne` with `relations: ['coach', 'trainingType']` before returning the DTO. Without this the response shape would be missing the nested coach/trainingType objects.
- **Test-time mutation gotcha**: when mocking `scheduleRepo.findOne` to return the same `existing` object, the service's in-place mutation of `existing.startTime` would leak into subsequent reloads and break event-payload assertions. Test mock spreads `{ ...existing }` on each call. Documented in the spec.
- **Pre-existing 6.1 lint debt unchanged**: env.validation max-len + admin-auth.service.spec import() annotation + 15 admin-side I/T-prefix violations. My new files lint-clean.
