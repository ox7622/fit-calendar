# Story 6.4: Schedule Management - Cancel & Delete Classes

## Status

ready-for-dev

## Story

**As a** club administrator,
**I want** to cancel or delete classes,
**so that** I can handle schedule changes and remove mistakes.

## Acceptance Criteria

1. `POST /api/v1/admin/schedule/:id/cancel` cancels a class. Body: `{ reason?: string }` (optional, free-text up to 500 chars).
2. Cancellation sets `status = 'cancelled'`, `cancellationReason = reason ?? null`. Both fields are now visible to all consumers (admin and Mini App) — Mini App-side display was already implemented in Stories 2.x and 3.x.
3. Cancellation is **idempotent**: cancelling an already-cancelled class returns 200 with the existing record, does NOT re-emit notification events.
4. **On cancel (only on the transition `scheduled → cancelled`), a `schedule.cancelled` event is emitted** with payload `{ scheduleEntryId, cancellationReason: string | null, snapshot: { className, startTime, coachName }, affectedUserIds: string[] }`. Story 5.5's listener consumes this to push notifications to subscribers.
5. **On cancel, all `pending` reminders for the class are deleted** (status='sent' and 'failed' rows are kept for audit). Deletion happens AFTER `affectedUserIds` is captured for the event payload.
6. `DELETE /api/v1/admin/schedule/:id` permanently deletes the class. Allowed only when the class has **no reminders at all** (sent, pending, or failed) AND is in the past. Otherwise returns 409 Conflict with a clear message: `"Класс нельзя удалить: есть напоминания. Используйте отмену."`
7. Both endpoints protected by `AdminAuthGuard`.
8. Admin UI: edit page (Story 6.3) gains a "Cancel Class" button (red, secondary action). Clicking opens a modal: optional reason textarea, "Confirm Cancel" / "Cancel" buttons.
9. After successful cancellation: navigate back to dashboard, toast `"Занятие отменено"`. Class now appears in the list with the cancelled visual treatment from Story 6.2 AC7.
10. "Delete Class" is a separate, more dangerous action — a kebab menu on the edit page with confirmation modal. Only enabled when AC6 conditions are met; otherwise show the constraint as a tooltip on the disabled menu item.

## Dev Notes

### Why cancel ≠ delete

The PRD and architecture are clear: cancellation is a soft state change with downstream effects (notifications, visible-but-strikethrough display). Delete is a hard remove only safe for orphan records. Conflating them lets an admin accidentally erase classes with notification history — bad for audit and bad for users who have already received a "your class is cancelled" message that now points to a deleted record.

### Why the event fires AFTER the DB transaction commits

If the event emit happens _inside_ the transaction:

-   Listener fires → bot sends notification → user gets "your class is cancelled"
-   Transaction rolls back due to a constraint violation or DB error
-   Class is still scheduled, but notifications have been sent

The user's experience: confused, complaint to support, broken trust. The fix: emit only after commit.

**`DataSource` injection pattern** — there's no existing transaction usage in the codebase yet, so the dev needs to set this up. NestJS+TypeORM idiom:

```typescript
import { DataSource } from 'typeorm';
import { InjectDataSource } from '@nestjs/typeorm';

@Injectable()
export class AdminScheduleService {
    constructor(
        @InjectRepository(ScheduleEntry) private readonly scheduleRepo: Repository<ScheduleEntry>,
        @InjectDataSource() private readonly dataSource: DataSource,
        private readonly eventEmitter: EventEmitter2,
        private readonly reminderService: ReminderService,
    ) {}

    async cancel(id: string, reason: string | null): Promise<AdminScheduleItem> {
        const entry = await this.scheduleRepo.findOne({
            where: { id },
            relations: ['coach', 'trainingType'],
        });
        if (!entry) throw new NotFoundException();
        if (entry.status === 'cancelled') return this.toDto(entry); // idempotent

        const affectedUserIds = await this.reminderService.findPendingReminderUsersByClass(id);
        const snapshot = {
            className: entry.trainingType.name,
            startTime: entry.startTime,
            coachName: entry.coach.name,
        };

        await this.dataSource.transaction(async (manager) => {
            await manager.update(
                ScheduleEntry,
                { id },
                {
                    status: 'cancelled',
                    cancellationReason: reason ?? null,
                },
            );
            // Pass the manager so the delete participates in this transaction:
            await this.reminderService.deletePendingByClass(id, manager);
        });

        // Now committed — safe to emit
        this.eventEmitter.emit(SCHEDULE_CANCELLED_EVENT, {
            scheduleEntryId: id,
            cancellationReason: reason ?? null,
            snapshot,
            affectedUserIds,
        });

        return this.toDto({ ...entry, status: 'cancelled', cancellationReason: reason ?? null });
    }
}
```

The key APIs: `@InjectDataSource()` from `@nestjs/typeorm`, `dataSource.transaction(callback)` from TypeORM, and `manager.update()` / `manager.getRepository(X)` for queries inside the transaction. `ReminderService.deletePendingByClass` accepts an optional `EntityManager` and uses it when present (otherwise falls back to its injected repo).

### Cascade safety net

The `Reminder` entity has `@ManyToOne(() => ScheduleEntry, ..., { onDelete: 'CASCADE' })`. This means a hard `DELETE` on a schedule entry would automatically remove all reminders for it via the FK constraint. Story 6.4's application-level guard (AC6) is the **primary** enforcement that prevents accidental delete-with-reminder-history. The DB cascade is a defensive safety net — if the application guard ever fails or is bypassed, the DB stays consistent rather than orphaning reminder rows.

This means: don't try to "tighten" the cascade to `RESTRICT`. The current `CASCADE` + application guard combination is correct.

### Why we capture `affectedUserIds` BEFORE deleting reminders

If we delete first, we lose the data we need to notify. The order in `cancel()`:

1. Load class (with relations for snapshot)
2. Capture `affectedUserIds` from pending reminders
3. Build payload
4. Transaction: update status, delete reminders
5. Emit event

Test for this exact ordering (Task 6) — it's the kind of bug that's invisible during dev (event still emits, no errors) but the listener gets an empty `affectedUserIds` array.

### Why delete is severely constrained

PRD AC6: "Allowed only when the class has no reminders at all AND is in the past." Three reasons:

1. Past + no reminders = a record nobody cares about. Safe to remove.
2. Future class with no reminders: still cancel-not-delete, because cancellation is the explicit signal to stop showing it.
3. Any class with reminder history (sent, pending, failed): the reminder rows reference this scheduleEntryId via FK. Deleting would either CASCADE wipe the audit trail or fail noisily. Either way, cancel is the right move.

The 409 message is in Russian per AC6 and points the admin to the right action.

### Idempotency on cancel

PRD doesn't explicitly require idempotency, but it's the right behavior: if the admin clicks "cancel" twice in quick succession (network lag, double-click), the second request should not double-emit notifications. AC3 makes this explicit.

### Endpoint contracts

**`POST /api/v1/admin/schedule/:id/cancel`** body:

```json
{ "reason": "Тренер заболел" }
```

→ 200 with the updated entry. Errors: 401, 404.

**`DELETE /api/v1/admin/schedule/:id`** → 204. Errors: 401, 404, **409** (`"Класс нельзя удалить: есть напоминания. Используйте отмену."`).

### What this story does NOT do

-   No "uncancel" / restore action — admin must create a new entry. Cancellation is one-way for MVP.
-   No bulk cancel (e.g. "cancel all classes by this coach for the week"). One at a time.
-   No notification sending — that's all on the Story 5.5 listener.
-   No reminder restoration if a delete fails partway — atomic transaction prevents that scenario.
