# Story 6.5: Coach Management

## Status

Ready for Review

## Story

**As a** club administrator,
**I want** to add and edit coach profiles,
**so that** members see accurate information about who teaches at the club.

## Acceptance Criteria

1. `GET /api/admin/coaches` returns all coaches (active + inactive) with `{ id, name, bio, photoUrl, specializations, certifications, isActive, createdAt, updatedAt }`. Sorted by `name ASC`.
2. `GET /api/admin/coaches/options` returns `{ id, name }[]` of **active** coaches only — used by Story 6.3's class form dropdown.
3. `GET /api/admin/coaches/:id` returns a single coach.
4. `POST /api/admin/coaches` creates a coach with `{ name, bio?, specializations: string[], certifications: string[], isActive?: boolean }`. Defaults: `isActive=true`, empty arrays for the lists.
5. `PUT /api/admin/coaches/:id` updates name, bio, specializations, certifications, isActive.
6. `POST /api/admin/coaches/:id/photo` accepts a `multipart/form-data` upload (`file` field), uploads to Cloudinary at `fitcalendar/coaches/{coachId}` with face-aware crop to 400×400, and stores the resulting URL on `coach.photoUrl`. Returns the new photoUrl.
7. Deactivation (`isActive=false` via PUT) is a soft-delete: coach hidden from Mini App + dropdowns, existing schedule entries with this coach **remain** but the cancellation/edit flow on those entries is the admin's responsibility.
8. Hard delete (`DELETE /api/admin/coaches/:id`) is allowed only when the coach has zero schedule entries (past or future). Otherwise 409 with `"Тренер не может быть удалён: есть занятия. Используйте деактивацию."`
9. All endpoints protected by `AdminAuthGuard`.
10. Admin UI: `/admin/coaches` lists all coaches in a table; `/admin/coaches/new` and `/admin/coaches/:id` provide forms with name, bio, specializations (chip input), certifications (chip input), photo upload, isActive toggle.
11. Photo upload widget: drag-and-drop or click-to-upload; client-side validation (max 5MB, image MIME types only); immediate preview; replaces existing photo on save.

## Dev Notes

### Cloudinary — why not local file storage

Architecture §7.3 mandates Cloudinary. Don't even consider local storage:

-   API instances will be ephemeral (containers, autoscaling) — local files don't survive
-   No CDN benefits, no auto-format/quality tuning
-   Backups become a separate concern

If Cloudinary credentials aren't configured in dev, the upload endpoint should 503 with a clear message rather than silently failing or saving garbage. Photo-less coach records are perfectly viable for local development.

### The `options` endpoint is a deliberate split

`GET /admin/coaches` returns the full coach record (with bio, photo, etc) — too much for a dropdown. `GET /admin/coaches/options` returns just `{ id, name }` for the lightweight UI consumer. Same pattern in Story 6.6 for training types. Don't conflate.

### Soft delete vs hard delete (AC7, AC8)

-   **Deactivate (`isActive=false`):** the everyday operation. Coach leaves the club, admin flips the toggle, all existing classes (past attendance, future scheduled) keep their reference. The coach disappears from the member-facing app.
-   **Hard delete:** only for "I created this by mistake, never used it." If schedule entries exist, the FK relationship would either break (coachId becomes invalid) or CASCADE wipe history — both bad. The 409 forces the admin to use deactivation.

### Chip inputs — don't add a lib

For specializations and certifications, `react-tag-input` / `react-select/creatable` etc. are tempting. They're 80KB minified for a feature you can write in 30 LOC:

```tsx
function ChipInput({ values, onChange }) {
    const [draft, setDraft] = useState('');
    const add = () => {
        const v = draft.trim();
        if (v && !values.includes(v)) onChange([...values, v]);
        setDraft('');
    };
    return (
        <div className="border rounded-xl p-2 flex flex-wrap gap-1">
            {values.map((v) => (
                <span key={v} className="bg-primary/20 text-primary rounded-md px-2 py-0.5 text-sm">
                    {v}
                    <button onClick={() => onChange(values.filter((x) => x !== v))}>×</button>
                </span>
            ))}
            <input
                value={draft}
                onChange={(e) => setDraft(e.target.value)}
                onKeyDown={(e) => e.key === 'Enter' && (e.preventDefault(), add())}
                onBlur={add}
                className="flex-1 outline-none bg-transparent text-sm"
            />
        </div>
    );
}
```

That's the whole component. Skip the lib.

### Completion Notes List

-   **Cloudinary credentials optional in dev**: env vars added as `@IsOptional` and the upload route returns 503 with a Russian message if any of the three is unset. API still boots without them.
-   **Lazy Cloudinary configuration**: `cloudinary.config({...})` is called on first upload rather than at module init, so a misconfigured dev box doesn't crash the API on boot. Subsequent uploads reuse the configured singleton.
-   **Deterministic Cloudinary folder**: `fitcalendar/coaches/{coachId}` with `overwrite: true` and `public_id: 'profile'` means each coach has exactly one persistent photo URL — re-uploading replaces in place rather than leaving orphan assets.
-   **Route ordering matters**: `GET /admin/coaches/options` declared before `:id` so NestJS doesn't route `'options'` as a UUID param (would fail ParseUUIDPipe with a confusing 400).
-   **Soft vs hard delete (AC7/AC8)**: deactivation is a metadata flip with no side effects on schedule entries; hard delete is gated by `ScheduleEntry.count > 0 → 409` with a Russian guidance message. The 6.5 edit page exposes the hard-delete button, which simply surfaces the 409 if not allowed.
-   **ChipInput is hand-rolled (~30 LOC)** as the story Dev Notes prescribe. Backspace-removes-last-chip when the draft is empty (common chip-input affordance).
-   **CoachPhotoUpload optimistic preview**: shows the local `URL.createObjectURL` while uploading, swaps to the returned Cloudinary URL on success, reverts to `currentUrl` on failure. Validates MIME (`image/*`) and 5 MB cap client-side before sending.
-   **New `adminApiClient.upload(path, FormData)` method**: separate from the JSON helpers because multipart needs the browser to set the boundary in `Content-Type` — sets `Authorization` only, never `Content-Type`.
-   **Photo upload only after create**: in CoachNewPage `onPhotoUpload` is undefined so CoachForm renders an explanatory hint instead of the upload widget — you can't upload a photo for a coach that doesn't exist yet. Edit page wires the upload through the real API call.
-   **Multer types**: `@types/multer` added as a dev dep; both `tsconfig.app.json` and `tsconfig.spec.json` had to include `"multer"` in their `types` array (default tsconfig only loaded `["node"]`).
-   **6.3 dropdown wired (Task 14)**: ScheduleForm's coachId text input is replaced with a real `<select>` populated by `adminCoachesApi.getOptions()`. ScheduleFilters had no coach filter yet (deferred since 6.2) so nothing to wire there. trainingTypeId text input stays — that's 6.6's job.
