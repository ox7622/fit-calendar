# Story 6.6: Training Types & Metadata Management

## Status

ready-for-dev

## Story

**As a** club administrator,
**I want** to manage training types (yoga, strength, etc.) with their difficulty, impact types, and equipment,
**so that** the schedule offers consistent, accurate categorization for members.

## Acceptance Criteria

1. `GET /api/v1/admin/training-types` returns all training types (active + inactive) sorted by `name ASC`.
2. `GET /api/v1/admin/training-types/options` returns active training types as `{ id, name }[]` for dropdown consumers (Story 6.3 schedule form).
3. `GET /api/v1/admin/training-types/:id` returns a single training type.
4. `POST /api/v1/admin/training-types` creates with `{ name, description?, difficulty, impactTypes, equipment, isActive? }`.
5. `PUT /api/v1/admin/training-types/:id` updates the same fields.
6. `difficulty` is restricted to `'beginner' | 'intermediate' | 'advanced'`. `impactTypes` is a subset of `['cardio', 'strength', 'flexibility', 'balance']`, at least one required. `equipment` is a free-form `string[]`, max 30 items, each ≤ 100 chars.
7. Deactivation (`isActive=false`) hides the type from member-facing dropdowns and Mini App; existing schedule entries with this type **remain** unchanged.
8. Hard delete (`DELETE /api/v1/admin/training-types/:id`) is allowed only when zero schedule entries reference this type. Otherwise 409 with `"Тип не может быть удалён: есть занятия. Используйте деактивацию."`
9. All endpoints protected by `AdminAuthGuard`.
10. Admin UI: `/admin/training-types` lists all with name, difficulty badge, impact icons, active status. Create + edit pages provide a form covering all fields.

## Dev Notes

### This is the simplest story in Epic 6

Pure CRUD with two enums and a guard against deletion-with-references. No file uploads, no events, no cross-module coupling beyond the schedule-form options endpoint. Should be a quick implementation if 6.5 has already established the chip-input pattern.

### Why we don't propagate metadata changes to existing schedule entries

If admin changes a training type's difficulty from `intermediate` to `advanced`, that's a metadata fix. Existing classes already advertised at `intermediate` shouldn't retroactively change difficulty in members' minds — but they DO inherit the new metadata via the entity relation. This is intentional: the data model has a single source of truth for training-type properties.

If the admin needs to "fix" this, they can either accept the change applies to all instances of that type (the common case — they're correcting a typo) or duplicate the type, deactivate the old, and migrate. We deliberately don't build a "snapshot at class creation" pattern — it's complexity that solves a problem we don't have.

### Sharing `ImpactTypeBadge` between admin and mini-app

The mini-app has `apps/mini-app/src/components/ImpactTypeBadge.tsx`. The admin needs the same visual component. Two options:

1. **Copy** to admin (~40 LOC of color tokens and icon mapping). Acceptable for MVP.
2. **Extract to a shared lib** (`libs/ui` exists). The cleaner path.

**Reality check on `libs/ui`:** it currently contains only a placeholder `Ui` component (`libs/ui/src/lib/ui.tsx` — "Welcome to Ui!"). Setting it up properly requires Tailwind config sharing, design token CSS, possibly a Vite/tsconfig-paths setup. That's its own ~30-min foundation task.

**Recommendation:** **copy `ImpactTypeBadge` into the admin app for 6.6** (5 min). Add a `TODO(libs/ui-foundation)` comment in both copies. When the project ever has 3+ components needing sharing, do the lib foundation work as a dedicated task.

Don't bundle the `libs/ui` setup into 6.6 — it would balloon the story for one component's worth of payoff.
