# Story 6.7: Club Information Management

## Status

ready-for-dev

## Story

**As a** club administrator,
**I want** to update the club's contact information, working hours, and location,
**so that** members always see accurate club details.

## Acceptance Criteria

1. `GET /api/v1/admin/club-info` returns the singleton ClubInfo record. If none exists yet, the API auto-creates a minimal default and returns it (admin shouldn't have to "create" the record).
2. `PUT /api/v1/admin/club-info` updates `{ name, address, phone?, workingHours, latitude?, longitude?, logoUrl? }`.
3. `workingHours` is a `Record<DayName, { open: string; close: string } | null>` where `DayName ∈ { monday, tuesday, wednesday, thursday, friday, saturday, sunday }`. `null` means closed that day. Times are `HH:mm` strings (24-hour).
4. `phone` validation: optional, but when provided must be E.164-style (start with `+`, followed by 7-15 digits) OR a plain `+7 XXX XXX-XX-XX` Russian formatted string. Accept both — the entity stores whatever the admin enters.
5. `latitude` and `longitude` validation: both required-together or both null. Latitude in `[-90, 90]`, longitude in `[-180, 180]`. Decimal numbers.
6. Logo upload via `POST /api/v1/admin/club-info/logo` (multipart, `file`) — same Cloudinary integration as Story 6.5's coach photo, but to folder `fitcalendar/club` and with a different transformation (logo: 200×200, `crop: 'fit'`, no face gravity).
7. Both endpoints protected by `AdminAuthGuard`.
8. Admin UI at `/admin/club` provides a form with all fields. Working hours UI is a 7-row block (one per day) with an open/closed toggle and two time pickers.
9. After save: success toast `"Сохранено"`, stay on the page (no redirect — admin may continue editing).

## Dev Notes

### Why a singleton with auto-create

ClubInfo is one row, period. Architecture data model treats it as such. The auto-create-on-first-GET pattern (AC1) means a fresh deployment doesn't require a manual seed step for the admin to see the page. The seed script may also create one — that's fine, `findOne` returns the existing one.

### Working hours data shape — match what the Mini App already expects

`ClubInfo.workingHours` is a JSONB column with the shape `Record<string, { open: string; close: string } | null>`. The Mini App's club page (Story 4.4) already renders this. **Do not change the shape** — admin form serializes to exactly this format.

```json
{
    "monday": { "open": "09:00", "close": "22:00" },
    "tuesday": { "open": "09:00", "close": "22:00" },
    "wednesday": { "open": "09:00", "close": "22:00" },
    "thursday": { "open": "09:00", "close": "22:00" },
    "friday": { "open": "09:00", "close": "22:00" },
    "saturday": { "open": "10:00", "close": "20:00" },
    "sunday": null
}
```

The day keys are lowercase English (matches the JSONB convention from the seed script). The UI translates labels to Russian for display only.

### No bot/event side-effects

This is the only Epic 6 story with zero downstream notification or event coupling. Pure state edit on a singleton. Quick to ship.

### Why the logo upload is decoupled from the main save

If the admin uploads a 4MB logo, then types into the address field, then clicks Save, you don't want to re-upload the logo every save. Two patterns to handle this:

1. **Separate endpoint, immediate upload (chosen):** `POST /admin/club-info/logo` returns the URL, frontend stamps it onto the form state. Save sends only the textual fields.
2. Form holds the `File` object, save sends multipart. More complex client logic, more client-server coupling.

Option 1 mirrors what Story 6.5 does for coach photos; consistent and simple.

### Lat/lon validation — why "both or neither"

The Mini App's "Show on Map" feature (Story 4.5) is gated on having coordinates. A single coordinate is unusable. AC5 enforces this at the API; the form reinforces it client-side for friendly UX.
