# Story 7.2: Customer CRUD + Telegram Phone Linking

## Status

ready-for-dev

## Story

**As a** club administrator,
**I want** to manage the club's customer records (name, phone, email) directly in the admin panel,
**so that** the system has a complete and authoritative list of members regardless of who has used the Mini App.

**As a** Mini App user,
**I want** to link my Telegram account to my customer record by entering my phone number once,
**so that** the app can show me my membership and personalized features without anyone having to register me a second time.

## Acceptance Criteria

1. New entity `Customer` replaces the old `User` entity. Fields: `id, firstName, lastName, phone, email, telegramId, telegramUsername, isActive, notes, createdAt, updatedAt`. **`phone` is unique and required.** `telegramId`, `telegramUsername`, `email`, `lastName`, `notes` are nullable.
2. `TelegramAuthGuard` no longer auto-creates records. On every request, it validates initData and looks up the customer by `telegramId`. If not found, the request continues with `request.customer = null` and `request.telegramIdentity` populated from initData.
3. **Customer-required endpoints** (reminders, profile, settings) reject unlinked requests with **403 + machine code `CUSTOMER_NOT_LINKED`**. Anonymous-OK endpoints (schedule, coaches, club info, plans) continue to work.
4. `GET /api/v1/me` returns `{ linked: true, customer: {...} }` for linked users, `{ linked: false, telegramIdentity: { firstName, username } }` for unlinked.
5. `POST /api/v1/me/link-phone { phone: "..." }` looks up a customer by normalized phone and links the calling Telegram identity if available. Returns the linked customer on success.
6. Phone normalization: any of `+7 495 123-45-67` / `8 495 1234567` / `+74951234567` / `89951234567` normalize to canonical `+7XXXXXXXXXX`. Both customer-creation (admin) and phone-lookup (member) use the same normalizer.
7. Linking errors:
    - **404** `PHONE_NOT_FOUND` — phone has no matching customer ("Этот номер не зарегистрирован. Обратитесь на ресепшн.")
    - **409** `PHONE_ALREADY_LINKED_TO_OTHER` — customer with this phone is already linked to a different Telegram identity ("Этот номер уже привязан к другому аккаунту. Свяжитесь с админом.")
    - **400** `INVALID_PHONE_FORMAT` — phone can't be normalized
8. Admin: `GET /api/v1/admin/customers` returns paginated customer list with search by name/phone/Telegram username. Filters: `isActive`, `linkedOnly` (has telegramId).
9. Admin: `POST /api/v1/admin/customers` creates a customer (phone required + normalized; telegramId optional). `PUT` updates fields. `DELETE` allowed only if no memberships, no reminders. Otherwise 409.
10. Admin UI: `/admin/customers` lists customers with filter/search; `/admin/customers/new` and `/admin/customers/:id` provide forms.
11. Admin can **unlink** (clear `telegramId` from a customer) via a dedicated button on the edit page. Used when a member needs to re-link from a new Telegram account.
12. Reminder entity's foreign key column renames from `userId` → `customerId`. The semantic meaning is the same; the rename clarifies that reminders are owned by club customers, not transient app users.

## Dev Notes

### This is the architectural pivot

Story 1.5 (Done) auto-upserted Telegram-authenticated users into a `User` table. That model treated "anyone who opens the app" as a customer. The product reality is different: customers are paying members tracked by reception, and Telegram identity is just a way for them to identify themselves at runtime.

This story renames the entity, splits the auth flow (anonymous vs linked), and introduces the explicit linking step. It's the foundation Epic 7 builds on top of.

**Story 1.5's QA gate becomes partially invalidated.** The auto-upsert behavior it certified is now wrong. Update the story 1.5 status to "Done — superseded for auth flow by 7.2" or similar after this lands.

### Why phone match (not username, not activation code)

| Option            | Rejection reason                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------ |
| Telegram username | Many users don't have one set; reception has to ask twice; usernames change                            |
| Activation code   | Extra UX step; admin has to generate + distribute; codes can be lost/leaked                            |
| **Phone match**   | Reception already collects phone for paying members; member already knows their own phone; one-shot UX |

The trade-off is: members typing a phone wrong on first attempt. The error UX (404 with "обратитесь на ресепшн") handles that gracefully.

### Why anonymous browsing stays

Brief explicitly says "Anonymous browsing is acceptable; users don't need accounts for MVP." Removing it for non-customers would mean prospective members can't see the schedule or plan options before deciding to sign up. Keeping it costs almost nothing.

### Auth flow contract — three states

| State                           | Recognized by                               | request.telegramIdentity | request.customer | Allowed routes                                            |
| ------------------------------- | ------------------------------------------- | ------------------------ | ---------------- | --------------------------------------------------------- |
| **Anonymous (not in Telegram)** | initData absent or malformed                | undefined                | undefined        | None — `TelegramAuthGuard` rejects with 401               |
| **Telegram-only (not linked)**  | Valid initData, no matching customer        | populated                | null             | Anonymous-OK routes (schedule, coaches, club, plans, /me) |
| **Linked customer**             | Valid initData, customer.telegramId matches | populated                | populated        | All routes including reminders, profile, settings         |

Anonymous-OK routes use `TelegramAuthGuard` only. Customer-required routes use `TelegramAuthGuard + RequiresLinkedCustomer`.

### Why `/me/*` instead of `/users/*`

Story 1.5 + 5.2 use `/users/*`. After this story, the entity is `Customer`, not `User`. Routes rename to `/me/*` for clarity (it's "my stuff," whoever I am — anonymous or linked). The decorator pattern is the canonical way to identify the calling user; the URL path doesn't need to.

### Phone normalization edge cases

The normalizer should be strict: if input doesn't normalize to a Russian (`+7XXXXXXXXXX`) shape, reject with 400. **Don't try to handle international numbers in MVP.** A single-club, single-region product doesn't need it. If the club ever has international members, revisit.

### Cross-story impact (load-bearing — read carefully)

This story changes the assumed auth model in Stories 5.1, 5.2, 5.6. Specifically:

-   **5.1 (Reminder Subscription):** `@TelegramUser()` becomes `@Customer()`; reminder service queries by `customerId`; user-not-linked case returns 403 (not 401). Frontend disables button + shows "link your profile" tooltip when `!customer`.
-   **5.2 (Reminder Time Preferences):** Routes move from `/users/settings` to `/me/settings`. Same auth requirement.
-   **5.6 (My Reminders List):** Same as 5.1.

If 5.1/5.2/5.6 ship before 7.2: they use the old User model and need to be patched when 7.2 lands.
If 7.2 ships first: 5.1/5.2/5.6 use the new Customer model from the start (cleaner — recommended).

**Recommended sequence: 6.1 (admin auth) → 7.1 (plan catalog) → 7.2 (this story) → 5.x (reminders, with the new Customer model) → 7.3+ (CSV, membership, usage tracking) → 6.2-6.7 (admin schedule/coach management).**

### What this story does NOT do

-   No membership / plan assignment — that's 7.4
-   No usage tracking — 7.5/7.6
-   No CSV import — 7.3
-   No self-registration flow — explicitly post-MVP
-   No admin user-management for staff (the AdminUser entity stays separate from Customer)
