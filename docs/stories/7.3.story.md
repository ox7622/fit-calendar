# Story 7.3: Customer CSV Bulk Import

## Status

Ready for Review

## Story

**As a** club administrator,
**I want** to bulk-import the club's existing customer list from a CSV file,
**so that** I don't have to type 200 members one-by-one when launching the system.

## Acceptance Criteria

1. Admin uploads a CSV file via `POST /api/admin/customers/import` (multipart, field `file`).
2. CSV is **dry-run by default**: the response is a preview showing what would happen — `{ rowsTotal, rowsToCreate, rowsToUpdate, rowsToSkip, errors }`. No DB writes happen yet.
3. Admin reviews the preview and submits with `?commit=true` (or via a "Confirm import" button) to actually apply.
4. Required CSV columns: `firstName`, `phone`. Optional columns: `lastName`, `email`, `telegramUsername`, `notes`. Order is **column-name-driven**, not positional. Extra columns are ignored.
5. Phone is normalized via the same helper from Story 7.2 Task 2. Rows with phones that fail normalization land in the errors list, **not** in the import.
6. Upsert key is **normalized phone**. If a row's phone matches an existing customer, the import updates only the columns present in the CSV (preserves existing `telegramId`, etc.). If no match, creates a new customer with `isActive=true`.
7. Within a single CSV, duplicate phones (after normalization) are reported as errors and the **second-and-later occurrences are skipped**. The first occurrence is processed.
8. Import is wrapped in a transaction — if any unexpected error occurs mid-commit, the whole batch rolls back.
9. Maximum file size: 5MB. Maximum row count: 5000. Larger files rejected with 413/400.
10. Both the dry-run preview and the commit response include a structured per-row error report: `[{ row: number, column?: string, message: string }]`. Admin UI displays this clearly so the admin can fix the CSV and retry.
11. Endpoint protected by `AdminAuthGuard`.

## Dev Notes

### Why dry-run by default

CSV imports are exactly the kind of operation where one fat-finger ruins your data. A two-step pattern (dry-run → confirm) is slow but defensible — admins read the summary and the errors before committing. For 200 customers this takes 30 seconds; for 50 imports a year that's 25 minutes total of friction in exchange for reliable data.

If you remove the dry-run for "convenience," you'll regret it the first time someone uploads a malformed CSV without realizing it.

### Why upsert by phone, not email or name

-   Phone is the linking key (Story 7.2). Source of truth.
-   Email is optional and many members won't have one.
-   Name is too ambiguous; "Maria Ivanova" appears multiple times in any club of size.

### Why the upload re-runs on commit (not stateful)

Stateless server is simpler. The cost is one extra HTTP upload of a 5MB-max file (~1 second). The alternative (server-side staging table with TTL) adds complexity for marginal UX benefit. If imports become a daily operation that admins want to be faster, revisit.

### What this story does NOT do

-   No membership assignment via CSV (just customer records). Story 7.4 is the assignment workflow; CSV import for membership rows is a Phase 2 stretch.
-   No backfill of `telegramId` from CSV — that field only gets populated by Mini App linking (Story 7.2).
-   No deletes via CSV — too dangerous. Admin uses the UI for that.
-   No history / undo of previous imports — accept the consequence of a bad import is to manually fix.

### Endpoint contract

**`POST /api/admin/customers/import`** (multipart, field `file`)

Without `?commit=true` (dry-run):

```json
{
    "rowsTotal": 152,
    "rowsToCreate": 145,
    "rowsToUpdate": 0,
    "rowsToSkip": 7,
    "errors": [
        { "row": 12, "column": "phone", "message": "Неверный формат телефона: \"abc\"" },
        { "row": 47, "column": "firstName", "message": "firstName не указан" }
    ]
}
```

With `?commit=true`:

```json
{
    "created": 145,
    "updated": 0,
    "skipped": 7,
    "errors": [...]
}
```

Errors: 400 (no file, file too large, > 5000 rows, malformed CSV unparseable), 401 (no auth).

### Completion Notes List

-   **Stateless commit per story Dev Notes**: the same file is re-uploaded with `?commit=true` after the dry-run preview. No server-side staging table; admin clicks "Применить" → file POSTs again → `parseAndValidate` re-runs → `commit` applies inside a `dataSource.transaction`. 5MB CSV re-uploads in ~1s; admin clicks twice instead of once.
-   **Service exposes both stages**: `parseAndValidate(buffer)` is pure (no writes) and `commit(plannedRows, manager)` takes an EntityManager so the caller controls the transaction. Controller does the transaction wrap so the service stays manager-aware-only.
-   **Bulk existence lookup**: instead of one `findOne` per row, a single `find({ where: { phone: In(phones) } })` classifies every row's create-vs-update in one round-trip. Important for the 5000-row ceiling.
-   **Update preserves `telegramId`/`telegramUsername` on omission**: the commit patch object only includes fields the CSV provided. Story 7.2's linking is decoupled — a CSV that doesn't carry `telegramUsername` shouldn't clobber a linked customer's Telegram identity.
-   **In-batch duplicate phones**: first occurrence wins, subsequent ones land in `errors` with a "впервые в строке X" pointer. Caught by `phoneFirstSeenAt` map in the first pass — no second scan needed.
-   **Per-row error categorization** (AC10) all in Russian: missing required header, missing required value, invalid phone, duplicate. Frontend renders them in a scrollable table.
-   **Excel BOM-friendly**: the parser strips a leading UTF-8 BOM so CSVs exported from Excel (which always adds one) don't read the first header as `<BOM>firstName`.
-   **Papaparse `delimiter: ','` is explicit**: otherwise auto-detection trips on single-column CSVs and reports a parse error.
-   **`fatal` filter on parsed.errors**: only `Quotes` / `Delimiter` parse errors abort. Per-row issues like `FieldMismatch` get re-reported in the structured errors array.
-   **"Apply correct rows only"**: if `errors.length > 0` but `rowsToCreate + rowsToUpdate > 0`, the apply button switches to "Применить (только корректные строки)" so admins can salvage a partial import (errored rows still skipped). If applicable rows is 0, only "Закрыть" shows.
-   **Sample CSV at `apps/admin/public/sample-customers.csv`** demonstrates all three accepted phone formats (`+7 999 555 12 34`, `+7 (495) 123-45-67`, `89991112233`) so admins can see what normalization accepts.
