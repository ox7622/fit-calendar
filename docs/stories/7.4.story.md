# Story 7.4: Membership Assignment + Mini App Profile

## Status

Ready for Review

## Story

**As a** club administrator,
**I want** to assign a customer to a plan with a start date and have the system compute their expiration automatically,
**so that** I don't have to do calendar math at the front desk and the customer's membership state is reliable.

**As a** club member,
**I want** to see my current plan, what features it includes, how many guest visits I have left, and when it expires,
**so that** I can plan my visits and renewals without asking reception.

## Acceptance Criteria

1. New entity `CustomerMembership` joins `Customer` ↔ `MembershipPlan` with: `id, customerId, planId, startDate, endDate, guestVisitsRemaining, freezeDaysRemaining, status (active | expired | cancelled), notes, createdAt, updatedAt, createdByAdminId`.
2. `endDate` is **computed at assignment time** from `startDate + plan.durationValue` in `plan.durationUnit` using `date-fns` (`addDays`, `addWeeks`, `addMonths`). Stored, not derived on read — so plan edits don't shift existing memberships.
3. `guestVisitsRemaining` is initialized to `plan.guestVisitsAllowed` at assignment. Same for `freezeDaysRemaining` from `plan.freezeDaysAllowed`. These are snapshots.
4. A customer **may have at most one `active` membership at a time**. Assigning a new one when an active membership exists either auto-cancels the old or rejects the request — see AC9 for the policy.
5. `POST /api/v1/admin/customers/:customerId/memberships` creates a membership. Body: `{ planId, startDate, notes? }`. Returns the created membership.
6. `GET /api/v1/admin/customers/:customerId/memberships` returns all memberships (history) for that customer, sorted by `startDate DESC`.
7. `PUT /api/v1/admin/memberships/:id` updates `endDate` (admin manual override — used during freeze in 7.6 and edge cases) and `notes`. Other fields are not editable; cancellation is a separate endpoint per AC10.
8. `POST /api/v1/admin/memberships/:id/cancel` sets `status='cancelled'`. Idempotent.
9. **Overlap policy** (AC4): when assigning a new membership, the API checks for an existing `active` membership for the customer. If one exists, the API returns **409 with code `ACTIVE_MEMBERSHIP_EXISTS`** and the body includes the existing membership's id + endDate. The admin UI prompts: "Cancel current membership and assign new?" — if confirmed, frontend calls `cancel` then `create`. **Two explicit user actions** rather than a single magic call.
10. Mini App: new `GET /api/v1/me/membership` returns the caller's current active membership (with embedded plan details + remaining counters + countdown info), or `{ membership: null }` if none. Requires linked customer (`RequiresLinkedCustomer` from 7.2).
11. Mini App: new profile page accessed via a profile icon in the `AppShell` header (top right). Shows:
    - First name + last name (from Customer)
    - Linked phone (read-only)
    - Current membership card: plan name, "Действует до DD MMM YYYY", countdown ("Осталось N дней"), features list, remaining guest visits, remaining freeze days
    - "Активного абонемента нет" + link to `/plans` if `membership === null`
    - Below the card: link to `/plans` to browse other options
    - Nothing else for now (settings stays accessible from the gear icon on `RemindersPage` per Story 5.2)
12. Status transitions: a membership is `active` if `today >= startDate && today <= endDate && status !== 'cancelled'`. Otherwise `expired` (after endDate) or `cancelled` (manual). The DB stores `status` as a literal column; a daily job (Task 9) flips `active → expired` automatically.
13. Both `POST` and `PUT` validate that `planId` references an active plan, that `startDate` is a valid date, and that `customerId` matches an active customer. Inactive coach/plan/customer references return 400.

## Dev Notes

### Why endDate is computed at assignment time, not derived

If we computed `endDate` on every read from `startDate + plan.duration`, then:

1. Plan edits would retroactively shift existing memberships (admin changes 6-month plan to 5-month → all existing 6-month members suddenly expire 30 days early).
2. Mid-membership freezes (Story 7.6) couldn't be represented — there's no place to store the shifted date.

Storing `endDate` as a snapshot solves both. The `addByUnit` helper does the math once at assignment.

### Why counters snapshot, not lookup

Same reasoning. If the plan's `guestVisitsAllowed` changes from 2 to 3, members who already used 2 of their 2 don't suddenly have 1 left. The membership's `guestVisitsRemaining` is its own state from the moment of assignment.

### Why two-step "cancel-then-create" instead of magic upsert

When the admin assigns a new plan to a customer who already has one, you have two paths:

| Path                  | Behavior                                                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Magic upsert**      | Server detects active membership, auto-cancels and creates the new one in one call                                                  |
| **Explicit two-step** | Server returns 409 with the existing membership info; client confirms with admin; admin confirms, client cancels and retries assign |

Magic is "smoother UX" but it makes the admin invisible to the consequence — they might not realize they just nuked someone's existing membership. Two-step makes the cancellation explicit. Worth the extra click.

### Why a daily expiration job, not on-read

Stored status has these benefits:

-   Admin lists / filters by status are consistent (no surprise "this looks active in the table but counts as expired in the detail view")
-   Reporting / analytics queries don't need a computed predicate everywhere
-   `getCurrentForCustomer` query is a simple `WHERE status='active'`

The daily flip is cheap (a single UPDATE with an indexed predicate). If the timing matters (e.g., a member shows up at 23:59 on their last day), the membership is still active at that moment. Day boundaries are coarse but plan durations are coarse anyway.

### What this story does NOT do

-   **No usage tracking** — that's 7.5 (guest visits) and 7.6 (freezes). This story just initializes the counters. Decrementing them is the next story's job.
-   **No payment / receipt generation** — explicitly Phase 3 per the brief.
-   **No "renew this membership" button** — admin manually creates a new one starting from the day after the old one expires. If renewal becomes a daily operation, add a one-click flow later.

### Completion Notes List

-   **Snapshot semantics**: `endDate` is computed via `addByUnit(startDate, plan.durationValue, plan.durationUnit)` at assign time and persisted, not derived on read. Same for `guestVisitsRemaining` / `freezeDaysRemaining` — they snapshot from the plan when assigned. This lets the plan template change later without retroactively shifting existing members.
-   **`assign` returns a discriminated result** (`{ status: 'created', membership }` | `{ status: 'active_exists', existingActive }`) so the controller can map active-exists into a 409 with the body the admin UI needs (`existingActive.id` + `endDate`). The "cancel-then-create" flow is explicitly two calls per Dev Notes — no magic upsert.
-   **`getCurrentForCustomer` is defensive**: orders by `endDate DESC` so even if multiple `active` rows somehow exist (manual DB edit, prior bug), the latest one wins and the UI stays usable.
-   **`updateMembership` is intentionally narrow**: only `endDate` and `notes` are editable. `endDate` is the field Story 7.6's freeze workflow shifts. Everything else stays as-snapshotted.
-   **Cancel is idempotent**: re-cancelling a cancelled membership returns the existing record without writes.
-   **Date column round-trip**: TypeORM surfaces Postgres `date` columns as JS Date set to midnight UTC. `normalizeDate` strips any time component before save, and `toMembershipResponse` uses `format(d, 'yyyy-MM-dd')` so the wire format is always date-only — no timezone drift.

-   **Stored status, not derived**: per Dev Notes — admin list/filter consistency outweighs the cost of a daily flip. A member who shows up at 23:59 on their last day is still active at that moment.
