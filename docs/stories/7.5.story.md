# Story 7.5: Guest Visit Logging

## Status

Ready for Review

## Story

**As a** club administrator,
**I want** to record when a member brings a guest, decrementing their remaining guest-visit count,
**so that** members can't exceed their plan's allowance and we have an audit trail of who used a guest visit and when.

## Acceptance Criteria

1. New entity `GuestVisit` with: `id, customerMembershipId, visitedAt (timestamptz, defaults to now), notes (nullable text), recordedByAdminId, createdAt`.
2. `POST /api/admin/memberships/:id/guest-visits` records a guest visit:
    - Body: `{ visitedAt?: ISO datetime; notes?: string }`. `visitedAt` defaults to current time if absent.
    - Decrements `customerMembership.guestVisitsRemaining` atomically (in a transaction with the GuestVisit insert).
    - Returns the new visit + the updated remaining count.
3. **Reject** with 400 + code `NO_GUEST_VISITS_REMAINING` when `guestVisitsRemaining === 0`.
4. **Reject** with 400 + code `MEMBERSHIP_NOT_ACTIVE` when membership status is not `'active'`. (Don't decrement an expired or cancelled membership.)
5. `GET /api/admin/memberships/:id/guest-visits` returns all visits for that membership, sorted by `visitedAt DESC`.
6. **Undo:** `DELETE /api/admin/guest-visits/:id` removes a visit and **increments** `guestVisitsRemaining` back. Returns the updated count. Used for fat-finger correction.
7. Admin UI on the customer membership card: a "+1 гостевой визит" button (only enabled when `guestVisitsRemaining > 0`) and a list of past visits with delete buttons.
8. Mini App `MembershipCard` (Story 7.4) updates immediately on next fetch — `guestVisitsRemaining` reflects the decrement. No live push needed.
9. All endpoints protected by `AdminAuthGuard`.

## Dev Notes

### Why row-level locking matters

Without `pessimistic_write` lock:

```
Admin A: SELECT remaining = 1
Admin B: SELECT remaining = 1
Admin A: UPDATE remaining = 0 → INSERT visit
Admin B: UPDATE remaining = 0 → INSERT visit
Final state: 2 visits inserted, only 1 decrement; remaining = 0 but should be -1 / rejected
```

This is unlikely with one reception desk, but trivially possible if two staff click at the same time. The lock costs ~1ms in Postgres and is the standard idiom for counter mutations.

### Why no separate "/admin/memberships/:id/guest-visits/:visitId/delete" route

Visit IDs are UUIDs (globally unique). The membership ID isn't needed for the delete operation. Keeping the URL flat (`DELETE /admin/guest-visits/:id`) reflects the actual operation. Same logic as why Story 6.4's class-cancel route doesn't need the customerId.

### Why we don't cap "increment" in undo

If admin records 3 visits then deletes 5 of them (somehow), `guestVisitsRemaining` could exceed `plan.guestVisitsAllowed`. Theoretically wrong but in practice:

-   Admin can't delete more visits than were recorded (constraint enforced by row existence)
-   If somehow `remaining > allowed` happens, the admin UI just shows "3 из 2 использовано" — visible as weird, fixable manually
-   Adding a cap would require knowing the plan's `guestVisitsAllowed` at undo time — extra fetch + extra logic for a case that shouldn't happen

YAGNI.

### Endpoint contracts

**`POST /api/admin/memberships/:id/guest-visits`** body:

```json
{ "visitedAt": "2026-05-02T14:30:00Z", "notes": "брат пришёл на йогу" }
```

Response 201:

```json
{
    "visit": { "id": "...", "visitedAt": "...", "notes": "...", "recordedByAdminId": "..." },
    "remaining": 1
}
```

Errors: 400 (`NO_GUEST_VISITS_REMAINING`, `MEMBERSHIP_NOT_ACTIVE`), 401, 404 (membership not found).

**`DELETE /api/admin/guest-visits/:id`** → 200 with `{ remaining: 2 }`. Errors: 401, 404.

### What this story does NOT do

-   **No member-side recording** — only admin can log a visit. No QR code at the door, no member self-attestation. Phase 2 if ever.
-   **No analytics** — "how many guest visits this month across all members" isn't a story. Just per-membership history.
-   **No notifications** — neither member nor admin gets a Telegram message when a visit is recorded.
