# Story 7.6: Membership Freeze Workflow

## Status

ready-for-dev

## Story

**As a** club administrator,
**I want** to freeze a member's membership for a defined period when they're traveling or injured, shifting their expiration date forward by the same amount,
**so that** members feel fairly treated and the system tracks freeze entitlements accurately.

## Acceptance Criteria

1. New entity `FreezeEvent` with: `id, customerMembershipId, startDate (date), endDate (date), durationDays (int), notes (nullable), recordedByAdminId, createdAt`. Stored separately from the membership for audit / multi-history visibility.
2. **Single contiguous freeze model**: a membership can have **at most one freeze of up to `freezeDaysRemaining` days**, started once. Once that freeze is consumed (fully or partially), no further freezes are allowed for that membership. Re-freezing is post-MVP.
3. `POST /api/v1/admin/memberships/:id/freezes` records a freeze:
    - Body: `{ startDate: ISO date string; durationDays: number; notes?: string }`
    - `endDate = startDate + (durationDays - 1)` (inclusive day range)
    - Membership's `endDate` shifts forward by `durationDays`
    - `freezeDaysRemaining` decremented by `durationDays`
    - Insert FreezeEvent + update membership atomically (single transaction)
4. **Reject** with 400 + code `INSUFFICIENT_FREEZE_DAYS` when `durationDays > freezeDaysRemaining`.
5. **Reject** with 400 + code `MEMBERSHIP_NOT_ACTIVE` when status is not `'active'`.
6. **Reject** with 400 + code `FREEZE_ALREADY_USED` when membership already has a recorded `FreezeEvent` (per AC2 single-freeze rule).
7. **Reject** with 400 + code `INVALID_DURATION` when `durationDays < 1` or non-integer.
8. `GET /api/v1/admin/memberships/:id/freezes` returns freeze events for that membership (will be 0 or 1 for MVP).
9. **Undo:** `DELETE /api/v1/admin/freezes/:id` reverses a freeze:
    - Increments `freezeDaysRemaining` back by the freeze's `durationDays`
    - Shifts membership's `endDate` backward by `durationDays`
    - Deletes the FreezeEvent
10. Admin UI: a "Заморозить" button on the active membership card. Clicking opens a modal with start date + duration inputs. After save, the membership card visibly shows "Заморожено: DD MMM – DD MMM ({durationDays} дней)" and the new `endDate`.
11. Mini App `MembershipCard` (Story 7.4) updates `freezeDaysRemaining` and `endDate` to reflect the freeze on next fetch. **Optionally**, if the freeze is currently active (`today ∈ [freeze.startDate, freeze.endDate]`), display a yellow "Заморожен" banner on the card.
12. All endpoints protected by `AdminAuthGuard`.

## Dev Notes

### Why "single contiguous freeze" for MVP

Two reasons:

1. **Modeling simplicity** — one freeze per membership = one row, one decrement, easy undo. Multiple freezes summing to ≤ allowance requires running totals + UI showing freeze history + edge cases like "what if admin records overlapping freezes."
2. **Real-world adequacy** — most members who request a freeze do so once per membership cycle (vacation, injury). The 5% of cases where a member wants to split it across the year aren't worth the modeling cost in MVP.

If post-MVP usage shows multi-freeze is genuinely needed, the migration is small: drop the AC6 check, allow multiple FreezeEvent rows per membership, sum used days for the cap.

### The endDate-shift math

```
Original membership: Jan 1 → Dec 31 (12 months)
Freeze: Mar 1 → Mar 30 (30 days)
After freeze: Jan 1 → Jan 30 (next year)
freezeDaysRemaining: 30 → 0
```

The shift is exactly `durationDays`. We don't subtract any "consumed" portion of the freeze — even if the member returns early, the entitlement was used. (Equivalently, we'd let the admin record a 14-day freeze instead of 30 if they know the member will be back in 14 days. The system trusts the input.)

### Why the freeze reservation includes future starts

Members often plan freezes ahead ("I'm going to be in Crete for 2 weeks in June"). The endDate shift happens immediately at the time the freeze is _recorded_, not at the time it _starts_. This is a defensible simplification:

-   Member knows their new expiration immediately
-   No need for a daily job that activates pending freezes
-   Slight oddness: if the freeze is recorded today but starts in June, the membership "extends" before the member has actually started using it. In practice this just means the displayed endDate is the post-freeze date from the moment of recording.

If the member cancels the trip, admin can `undoFreeze` to revert.

### Inclusive vs exclusive endDate (AC3)

The math says `freezeEndDate = startDate + (durationDays - 1)` so a 7-day freeze starting Monday ends the following Sunday. The membership's `endDate` shifts by `durationDays` (not `durationDays - 1`) — those are subtly different. Test for this exact case.

### Why we don't auto-pause reminders during freezes

If a member is frozen but has reminders set for classes during the freeze period, what happens? Three options:

1. **Send reminders anyway** (current MVP behavior — reminder dispatcher is unaware of freezes)
2. Skip reminders during freeze
3. Cancel reminders entirely on freeze

For MVP we go with option 1. Reasoning: a "frozen" membership doesn't mean the gym is closed to them, just that their plan-time clock isn't ticking. They could still attend (uncommon but possible). Skipping reminders is a Phase 2 polish.

If you find yourself implementing freeze-aware reminder logic in 7.6, **stop** — it's out of scope.

### Endpoint contracts

**`POST /api/v1/admin/memberships/:id/freezes`** body:

```json
{ "startDate": "2026-06-01", "durationDays": 14, "notes": "отпуск" }
```

Response 201:

```json
{
    "freeze": { "id": "...", "startDate": "2026-06-01", "endDate": "2026-06-14", "durationDays": 14, "notes": "..." },
    "membership": { "id": "...", "endDate": "2027-01-14", "freezeDaysRemaining": 16 /* ... */ }
}
```

Errors: 400 (INSUFFICIENT_FREEZE_DAYS, MEMBERSHIP_NOT_ACTIVE, FREEZE_ALREADY_USED, INVALID_DURATION), 401, 404.

**`DELETE /api/v1/admin/freezes/:id`** → 200 with `{ membership }`. Errors: 401, 404.

### What this story does NOT do

-   No multi-freeze support — see "single contiguous" rationale above
-   No automatic prorated freeze (e.g., if member returns early, they don't get partial credit). Admin can `undoFreeze` and re-record with the actual duration if needed.
-   No notifications when a freeze starts/ends — Phase 2 if useful
-   No member-side request UI — this is admin-driven; the conversation happens at reception, not in the app
