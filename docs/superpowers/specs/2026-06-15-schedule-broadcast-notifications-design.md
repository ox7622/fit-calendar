# Рассылка уведомлений об изменениях расписания всем пользователям бота

**Дата:** 2026-06-15
**Статус:** утверждён дизайн, готов к плану реализации

## Проблема

Сейчас бот умеет уведомлять об изменениях расписания, но **только подписчиков** — клиентов,
у которых есть pending-напоминание (`Reminder`) именно на это занятие. Подписка появляется
лишь когда клиент сам включил напоминание через mini-app. На практике подписчиков почти нет,
поэтому уведомления никто не получает.

Дополнительно:
- Удаление занятия **запрещено**, если на него кто-то записан (`409`, «используйте отмену»),
  и не шлёт уведомлений вовсе.
- Создание нового занятия не уведомляет никого.

## Цель

Уведомлять **всех достижимых пользователей** (а не подписчиков) о значимых изменениях
расписания в ближайшем будущем, с явным подтверждением со стороны админа.

## Решения (зафиксированы с заказчиком)

1. **Получатели** — все клиенты с привязанным Telegram: `telegramId IS NOT NULL AND isActive = true`.
   Отдельной таблицы «все, кто нажал /start» в системе нет; достижимы только привязанные клиенты.
2. **Триггеры пуша** — создание, изменение времени/длительности, отмена, удаление занятия.
3. **Удаление** — снять блок `has_subscribers`: удаление разрешено и шлёт пуш всем.
4. **Окно уведомления** — пуш отправляется, только если итоговый `startTime` занятия в пределах
   `now ≤ startTime ≤ now + 5 дней`. Для переноса берётся **новое** время; для отмены/удаления —
   текущее. Изменения занятий дальше 5 дней проходят молча. Прошедшие занятия не уведомляются.
5. **Подтверждение в админке** — перед действием, попадающим в окно 5 дней, показывать
   предупреждение, что все пользователи бота получат пуш.

## Архитектура

Переиспользуем существующий конвейер **событие → листенер → персистентный outbox → cron-диспетчер**.
Он уже generic (`NotificationOutbox.customerId` nullable, `payload` — jsonb) и умеет ретраи с
бэкоффом и восстановление после рестарта (`NotificationOutboxService`, `NotificationOutboxDispatcher`).

Отвергнутые альтернативы:
- Отдельный `BroadcastService` со своим диспетчером — дублирует инфраструктуру ретраев.
- Синхронная отправка в запросе админа — блокирует запрос, нет ретраев, упирается в лимиты Telegram.

### Компоненты

**1. Источник получателей** — `CustomerService.findBroadcastRecipients()`
- Возвращает `{ customerId: string; telegramId: number }[]`.
- Фильтр: `telegramId IS NOT NULL AND isActive = true`.
- Одна точка истины для всех видов рассылки.

**2. Гейт окна** — чистая функция `isWithinNotifyWindow(startTime: Date, now: Date): boolean`
- `now ≤ startTime ≤ now + NOTIFY_WINDOW_DAYS` (`NOTIFY_WINDOW_DAYS = 5`).
- Живёт рядом с листенером (или в `reminder`-утилитах), покрыта юнит-тестами.
- **Серверный гейт — источник истины.** Клиент считает то же самое только для текста модалки.

**3. Единый листенер** — `ScheduleNotificationListener`
- Заменяет два текущих листенера: `ScheduleChangeNotificationListener` (Story 5.4) и листенер
  отмены (Story 5.5). Снимает дублирование «построить сообщение + положить в outbox».
- Обрабатывает 4 события через общий путь: гейт по `startTime` → если внутри окна, получить всех
  получателей → положить по строке в outbox с нужным текстом.
- Получатели теперь **все** (`findBroadcastRecipients`), а не подписчики
  (`findPendingByClassWithCustomer` / `affectedCustomerIds` больше не используются для рассылки).

**4. События** (`schedule.events.ts`) — четыре:
- `SCHEDULE_CREATED` — новое занятие (новое).
- `SCHEDULE_CHANGED` — изменилось время/длительность (есть).
- `SCHEDULE_CANCELLED` — отмена (есть).
- `SCHEDULE_DELETED` — удаление (новое).

Каждое событие несёт **снапшот** занятия (название, тренер, время), достаточный для текста
сообщения без повторного чтения (важно для `DELETED` — строки уже не будет).

**5. Эмиссия событий** — `AdminScheduleService` (только **одиночные** действия рассылают):
- `create` → `SCHEDULE_CREATED`.
- `update` → `SCHEDULE_CHANGED` (как сейчас, при изменении `startTime`/`durationMinutes`).
- `cancel` → `SCHEDULE_CANCELLED` (как сейчас).
- `deleteEntry` → снять блок `has_subscribers`; эмитить `SCHEDULE_DELETED` со снапшотом,
  собранным **до** удаления строки.
- Логика reminders (удаление pending при отмене, пересчёт `notifyAt` при правке) **остаётся** —
  это отдельная фича pre-class напоминаний, не пересекается с рассылкой.

**Массовые операции — без рассылки (housekeeping):**
- `bulkCreate` (заполнение календаря) и `bulkDelete` (чистка дублей) **не** шлют пуш: иначе
  одно действие = десятки пушей каждому пользователю, и под них не вписывается требование
  «модалка-подтверждение на действие».
- `bulkDelete` **сохраняет** текущий guard `has_subscribers` (не удаляем молча занятия, на которые
  кто-то записан). Снятие блока касается только одиночного `deleteEntry`.

**6. Outbox** — расширить тип уведомления
- `TOutboxNotificationType`: добавить `'schedule_created'`, `'schedule_deleted'`
  к существующим `'schedule_changed' | 'schedule_cancelled'`.
- Колонка `type` — `text`, миграция **не требуется**.

**7. Пропускная способность диспетчера**
- Сейчас `TICK_BATCH = 50`/мин, `SEND_CONCURRENCY = 5`. Рассылка на N человек растягивается на
  `N/50` минут.
- Поднять `TICK_BATCH` до значения, рассчитанного под число клиентов (предложение: 300 —
  это ~5 сообщений/с, втрое ниже лимита Telegram ~30/с). Точное значение подобрать при реализации.

### Тексты сообщений

- **created:** `🆕 Новое занятие` + название, время, тренер.
- **changed:** существующий `⚠️ Изменение в расписании` (было/будет, тренер).
- **cancelled / deleted:** `❌ Занятие отменено` + название, время, тренер; для `cancelled`
  добавляется причина, если указана.

Все с inline-кнопкой mini-app (`webAppUrl`), как сейчас в outbox-payload.

## Админка (фронтенд)

Общий шаг подтверждения перед действием, попадающим в окно 5 дней (клиент считает по `startTime`:
новое время для создания/правки/переноса, текущее — для отмены/удаления):

> ⚠️ Занятие в ближайшие 5 дней. Все пользователи бота получат пуш-уведомление об этом. Продолжить?

Вне окна — обычное подтверждение без предупреждения.

Точки применения:
- **Создание** — `CreateClassDialog`.
- **Правка времени/длительности** — `ScheduleEditPage` (сохранение).
- **Перенос** — `MoveClassConfirm` (расширить текст).
- **Отмена** — `CancelClassModal` (добавить строку предупреждения).
- **Удаление** — заменить `window.confirm('Удалить занятие безвозвратно?')` на нормальную модалку
  (компонент `Modal` уже есть) с условным предупреждением о пуше.

## Поток данных (пример: правка времени)

1. Админ меняет время в `ScheduleEditPage`, клиент видит «в окне 5 дней» → показывает модалку-предупреждение.
2. Подтверждение → `PUT /admin/schedule/:id`.
3. `AdminScheduleService.update` сохраняет, пересчитывает reminders, эмитит `SCHEDULE_CHANGED` (снапшот + новое время).
4. `ScheduleNotificationListener` проверяет `isWithinNotifyWindow(newStartTime)` → внутри окна.
5. Тянет `findBroadcastRecipients()` → кладёт по строке в `notification_outbox` (type=`schedule_changed`).
6. `NotificationOutboxDispatcher` (cron, каждую минуту) шлёт пачками с ретраями.

## Обработка ошибок

- Отправка одного получателя падает → outbox ретраит с бэкоффом до `OUTBOX_MAX_ATTEMPTS`, затем `failed`
  (поведение уже есть). Падение одного получателя не влияет на остальных.
- Эмиссия событий best-effort относительно ответа админу: ошибка постановки в очередь логируется,
  но не валит запрос (как в текущем change-листенере).
- `SCHEDULE_DELETED` со снапшотом до удаления — строки уже нет, но текст собирается из снапшота.
- Гонки отмены/правки/удаления — существующие транзакции с `pessimistic_write` (в `cancel`) сохраняются.

## Тестирование

Юнит-тесты:
- `isWithinNotifyWindow`: внутри окна, ровно на границе +5д, за окном, прошедшее занятие.
- `findBroadcastRecipients`: фильтрует по `telegramId` и `isActive`.
- `ScheduleNotificationListener`: по одному кейсу на каждый kind (created/changed/cancelled/deleted) —
  внутри окна (ставит N строк) и вне окна (не ставит ничего).
- Снятие блока удаления в `AdminScheduleService.deleteEntry`/`bulkDelete` (раньше `409` — теперь успех + событие).
- Обновить существующие тесты отмены/правки: получатели = все, а не подписчики.

Фронтенд:
- Модалка-предупреждение показывается в окне 5 дней и не показывается вне его — на всех пяти точках.

## Вне рамок (YAGNI)

- Глобальный opt-out от рассылки на уровне клиента (нет требования; `isActive` достаточно).
- Пер-занятийные настройки уведомлений.
- Тихие часы / дедупликация близких изменений.
- Решение прод-инцидента с webhook 502 (бот, по словам заказчика, работает; вынесено отдельно).
