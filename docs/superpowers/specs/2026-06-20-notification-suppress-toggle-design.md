# Per-action "don't notify" toggle for schedule changes

**Дата:** 2026-06-20
**Статус:** утверждён дизайн, готов к плану реализации
**Связано:** [2026-06-15-schedule-broadcast-notifications-design.md](./2026-06-15-schedule-broadcast-notifications-design.md)

## Проблема

Рассылка уведомлений всем пользователям при изменении расписания в ближайшие 5 дней
сейчас срабатывает автоматически. У админа нет способа внести правку в пределах окна
**без** пуша (например, мелкую корректировку), кроме как ждать, пока занятие выйдет за
5 дней, или пользоваться массовыми операциями. Модалка-подтверждение «всё или ничего»:
подтвердить = сохранить и отправить пуш; отмена = вообще не сохранять.

## Цель

Дать админу выбор «уведомлять или нет» для каждого действия, попадающего в окно пуша,
не меняя поведение по умолчанию.

## Решения (зафиксированы с заказчиком)

1. **Дефолт — уведомляем.** Чекбокс «Уведомить пользователей» включён по умолчанию; админ
   снимает галочку, чтобы промолчать. Поведение по умолчанию остаётся прежним.
2. **Охват — все 4 действия:** создание, изменение/перенос, отмена, удаление.
3. **Вне рамок:** глобальный рубильник и персональная отписка клиента.

## Архитектура

Прокидываем необязательный флаг `notify` (по умолчанию `true`) через каждый admin-эндпоинт
расписания. Сервис эмитит событие рассылки **только** когда `notify !== false`.

**Сервер — единственный авторитет.** Пуш уходит при выполнении обоих условий:
`notify === true` (на эмите в сервисе) **и** занятие в окне 5 дней (гейт в листенере).
Логика напоминаний и отмены (удаление pending-reminders, пересчёт `notifyAt`) флагом
не затрагивается — он гейтит только эмит широковещательного события.

Отвергнутые альтернативы: спец-заголовок или отдельные «silent»-эндпоинты — дублируют
контракт и усложняют клиент.

## Бэкенд

### DTO
- Добавить `notify?: boolean` (необязательное, `@IsOptional() @IsBoolean()`) в:
  - `CreateScheduleEntryDto`
  - `UpdateScheduleEntryDto`
  - `CancelClassDto`
- DELETE сейчас без тела → новый query-DTO `DeleteScheduleEntryQueryDto { notify?: boolean }`.
  Значение приходит строкой, поэтому coercion через `@Transform(({ value }) => value !== 'false' && value !== false)`
  (любое значение, кроме явного `false`, трактуется как `true`; отсутствие → `true`).
  Отдельный DTO обязателен: глобальный `ValidationPipe` работает с `whitelist + forbidNonWhitelisted`,
  поэтому новый query-параметр должен быть свойством DTO, иначе запрос отклонят.

### Сервис (`AdminScheduleService`)
- `create` / `update` / `cancel` / `deleteEntry` получают признак `notify` (из DTO/query).
- В каждом: `const notify = dto.notify ?? true;` и оборачиваем эмит:
  - `create`: `if (notify) this.eventEmitter.emit(SCHEDULE_CREATED_EVENT, ...)`
  - `update`: `if (notify && (startTimeChanged || durationChanged)) emit(SCHEDULE_CHANGED_EVENT, ...)`
  - `cancel`: `if (notify) emit(SCHEDULE_CANCELLED_EVENT, ...)` (удаление reminders и аудит — без изменений)
  - `deleteEntry`: `if (notify) emit(SCHEDULE_DELETED_EVENT, ...)`
- `bulkCreate` / `bulkDelete` не меняются (они и так молчат).
- Контроллер пробрасывает `dto.notify` (для DELETE — `query.notify`) в сервис.

### Обратная совместимость
`notify` отсутствует → трактуется как `true`. Существующие вызовы/тесты без флага
продолжают эмитить событие как раньше.

## Фронтенд (админка)

### `useConfirm` / `ConfirmDialog`
- Новая опция запроса `notifyToggle?: { label: string }`.
- Когда задана — диалог рендерит чекбокс (по умолчанию **включён**) с этим лейблом.
- Результат `confirm()` становится `{ confirmed: boolean; notify: boolean }`:
  - подтверждение → `{ confirmed: true, notify: <состояние чекбокса> }`
  - отмена/закрытие → `{ confirmed: false, notify: true }`
  - без `notifyToggle` → `notify` всегда `true` (вызыватель его игнорирует).
- Все вызыватели обновляются на новую форму результата.

### Точки и видимость
Чекбокс показывается **только когда занятие в окне 5 дней** (`isWithinNotifyWindow`) —
вне окна пуша нет, отключать нечего.
- **Создание** (`CreateClassDialog`) и **правка/удаление** (`ScheduleEditPage`) — confirm уже
  открывается только в окне; добавляем `notifyToggle` и пробрасываем `notify` в вызов API.
- **Отмена** (`CancelClassModal`) и **перенос** (`MoveClassConfirm`) — это собственные модалки;
  добавляем в них чекбокс (виден только в окне) и прокидываем `notify`.

### Admin API (`schedule.api.ts`)
- `create(payload, notify?)` → тело включает `notify`.
- `update(id, payload, notify?)` → тело включает `notify`.
- `cancel(id, reason, notify?)` → тело `{ reason, notify }`.
- `delete(id, notify?)` → при `notify === false` добавляет `?notify=false`.

## Поток данных (пример: правка времени без пуша)

1. Админ меняет время в окне 5 дней → `ScheduleEditPage` открывает confirm с чекбоксом
   «Уведомить пользователей» (включён). Админ снимает галочку, подтверждает.
2. `update(id, payload, /* notify */ false)` → `PUT /admin/schedule/:id` с `notify: false`.
3. `AdminScheduleService.update`: `notify=false` → reminders пересчитываются как обычно,
   но `SCHEDULE_CHANGED_EVENT` **не** эмитится.
4. Рассылки нет. (Если бы галочка осталась — событие ушло бы, листенер проверил окно и разослал.)

## Обработка ошибок
- Невалидный `notify` (не boolean) → 400 через `ValidationPipe`, как для прочих полей.
- Поведение по умолчанию (флаг отсутствует) безопасно: уведомляем.

## Тестирование

Бэкенд (unit):
- `AdminScheduleService`: для каждого из 4 действий — эмитит при `notify` undefined и `true`,
  **не** эмитит при `notify=false`; reminders/аудит при этом отрабатывают как прежде.
- `DeleteScheduleEntryQueryDto`: coercion `'false'→false`, `'true'→true`, отсутствие → `true`.

Фронтенд:
- `useConfirm`: с `notifyToggle` возвращает состояние чекбокса; без него — `notify=true`;
  отмена → `{ confirmed:false, notify:true }`.
- Чекбокс виден в окне 5 дней и скрыт вне его на всех четырёх точках; дефолт — включён.

## Вне рамок (YAGNI)
- Глобальный флаг включения/выключения уведомлений.
- Персональная отписка клиента в mini-app.
- Запоминание выбора админа между действиями.
